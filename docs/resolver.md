# Resolver

The resolver is in `crates/model/src/resolve` (pure, no I/O). It validates against the adapter registry that the CLI builds (`crates/cli/src/adapters.rs`, [docs/adapters.md](adapters.md)). [docs/architecture.md](architecture.md) is the contract. This page records only what the contract leaves open.

## Validation order

The first error follows DESIGN.md section 9.

1. Document and bundle schema: profile, bundle chain, core, selected modules and their prerequisites.
2. Selection and dependency validity: unknown, duplicate, platform, cycle. Every ID is checked for unknown before any is checked for duplicate, so the code does not depend on list order. A cycle error names only the modules on one cycle, not the modules that wait on it.
3. Composition authority and conflicts: overrides and contributions.
4. Resolved adapter schema and source containment.
5. Output claims.

## Error codes added by the resolver

The fixtures (`examples/cases.toml`) and the architecture fix the other resolver codes, including `E_ADAPTER_UNKNOWN`. The resolver adds these:

| Code | Meaning |
| --- | --- |
| `E_FIELD_UNKNOWN` | A key that schema 1 does not define (document or adapter value). |
| `E_MANIFEST_INVALID` | Missing or wrongly typed key, invalid ID, invalid policy path, a core that requires modules, duplicate bundle or resource ID. |
| `E_REFERENCE_INVALID` | A reference to the wrong kind of document, an unknown or unselected resource, a catalogue key that does not match the module ID, an invalid override path. |
| `E_TYPE_MISMATCH` | A value whose type differs from the owner's value or the adapter schema. Boolean and integer are different types. |
| `E_EXTENSION_CONFLICT` | A contribution to a key that already exists, or two contributors for one key. |
| `E_BUNDLE_CYCLE` | Bundles extend each other in a cycle. |
| `E_PLATFORM_MISMATCH` | The bound profile declares a platform or architecture that differs from this machine (the `Platform` port and `std::env::consts::ARCH`, where `aarch64` is written `arm64`). It is checked after resolution. `plan` and `apply` refuse with exit 3. `doctor` reports an ERROR row in the `profile` line, its plan row is UNKNOWN, and it exits 1. `explain` still works and prints the mismatch as a `note:`. `E_PLATFORM_UNSUPPORTED` is different: it refuses a module that does not list the profile's platform. |
| `E_REPORT_UNAVAILABLE` | A source or root cannot be read, so the requested report cannot be produced. Exit 2 (architecture section 10: "inability to produce the requested report"). Limit and trust failures while loading (`E_LIMIT_EXCEEDED`, `E_SOURCE_UNTRUSTED`) stay exit 3. |

Every other resolver code exits 3 (blocked before mutation, `Code::exit()`). `doctor` does not use that mapping: it reports a resolver error as an ERROR row and exits 1 ([docs/doctor.md](doctor.md)).

## Rules the architecture leaves open

Each item names the text it extends. None changes a fixture or a documented code.

1. **Module order.** DESIGN.md section 3 says "core is first and remaining ready modules are ordered lexically". The fixtures require `core, server, homelab` for the homelab case, so "ready" means "all prerequisites already placed", with lexical order among ready modules.
2. **Trusted root.** DESIGN.md section 4 says each source "remains within the supplying module's trusted root". The resolver takes that root to be the directory of the manifest that supplies the value: the module for a module value or override, the profile directory for a profile override (an inference, because the text names only modules). A bundle's `core` and catalogue paths stay inside the bundle directory. `extends` and the profile `bundle` may name any bundle in the materialized sources. The `source-containment` case does not separate a module root from a bundle root, because its path leaves both.
3. **`..` and symlinks.** The resolver never collapses `..` before it follows links. It resolves each step against the snapshot, as a filesystem does, and every hop must stay under the root.
4. **Core in selection.** `core` is implicit. Naming it in `modules` or `requires` is `E_MODULE_DUPLICATE`. A core with `requires` is `E_MANIFEST_INVALID`. A catalogue key `core` is `E_CORE_REPLACEMENT`.
5. **Override targets.** A module may override a default of any resource in the selected composition, including its own. Authority comes only from `policy.defaults`, never from `requires`.
6. **Contributions.** Only modules contribute. A profile has no `contributions` key (unknown key). The key must be `<contributor id>.` followed by `[a-z0-9][a-z0-9._-]*`. A contribution to a path not listed in `policy.extensions` is `E_OVERRIDE_FORBIDDEN`.
7. **Output paths.** In addition to DESIGN.md section 4, a target with a control character, a backslash or a leading `~` component is `E_TARGET_INVALID` (a printed backslash is doubled, so an operation id that holds one could not be pasted back as a flag). Claims are compared after Unicode lowercasing per component, and a claimed file may not also be the parent of another claim. Unicode normalization forms are not folded.
8. **Distribution claims.** `skills/v1` claims `<root>/<entry>` for each entry whose `enabled` is not `false`. A disabled entry has no claim.
9. **Limits.** Documents: 1 MiB, nesting depth 32, strings 64 KiB, 10,000 resources (counted from the selected modules before any resource is composed), bundle ancestry 16 (architecture section 5, S10). The resolver adds these bounds on cost: 10,000 modules including the core (9,999 others resolve, 10,000 others are refused), 64 MiB of module documents, 200,000 values, 100,000 claimed output paths per resource and 200,000 over the composition (checked from the roots and entries counts before any path is built), 1,000 include directives per authored native document and 10,000 over the composition (counted once per resource that links the document; each document is parsed once). All are refused with `E_LIMIT_EXCEEDED` before provenance is built. `explain` clips each text field to 200 characters and refuses a report over 100 resources or 1 MiB. The CLI source loader reads at most 20,000 entries, 1 MiB per file and 64 MiB in total.
10. **Source loading.** The loader opens each file with `O_NOFOLLOW` and `O_NONBLOCK` and confirms a regular file with fstat. It skips a top-level `.git` in any letter case, which is repository metadata. A `.git` deeper in the tree (any letter case) is a submodule or gitlink, which architecture section 8 rejects, so it is `E_SOURCE_UNTRUSTED`. A FIFO, device or socket is `E_SOURCE_UNTRUSTED`. So is a name, or the target text of a link, that holds a control character. A bundle can limit what the loader reads ("Source roots and excludes" below).
11. **Adapter schemas.** The resolver validates the effective `value` against a schema per adapter. The schemas are the keys the fixtures use. Native documents (`git-config/v1` and the managed and seed parts of `claude-settings/v1`) must be tables (`E_TYPE_MISMATCH` otherwise) and keep their types without key checks, because their keys belong to the application. The one exception is the empty key `""`, at any depth of a native table or in a map (for example a `skills/v1` entry): it is `E_MANIFEST_INVALID`, because the key has no JSON pointer.
12. **Secret-bearing resources.** `op-template/v1` values are references. `explain` prints `[redacted]` for them and the resolver records no content identity for them. The file mode must be an integer in `0..=0o777` with group and other bits clear and the owner read bit set (the output is read back after every write and at every plan).
13. **Source root.** `explain` and every other command that reads sources take the root from `--root <dir>`, else from the root the binding records (DFM-61). It must contain the bound profile. The profile comes from the binding. No `--profile` flag exists.
14. **Fragment directories.** `text-fragments/v1` reads fragments from `fragments_dir`; it does not write there. A blanket claim on the directory would reject the `work` module's fragment `.codex/AGENTS.d/40-work.md`, which `external-composition` requires to resolve, because supplying a fragment from another module is the purpose of the directory (DESIGN.md section 3). The directory is therefore claimed as a prefix with one exception: another resource may place a file directly in it when the file name matches the owner's `pattern`. Anything else collides: a non-matching name, a nested path, the directory itself, a case alias of those, a second assembler whose directory equals or nests with this one, the assembled file inside its own directory, and a file claimed above the directory (for example a link at `.codex` when the assembler reads `.codex/AGENTS.d`). A resource with secret values (`op-template/v1`) may not place a file in a fragment directory: the manager never reads a secret output, so it is `E_TARGET_COLLISION`. The pattern allows `*` and `?` only.
15. **Case.** One fold (`dfm_model::fold`: upper then lower case, which folds U+017F and the Kelvin sign) is used for source lookup, claims and the planner. Source lookup matches without regard to case, as a case-insensitive filesystem does. A link spelled `Link` is therefore followed for `link`, and two entries that differ only by case are `E_SOURCE_ESCAPE`. `..` applies only to a directory that exists in the snapshot.
16. **Display.** `dfm_model::display` holds one definition, used by resolver messages, `explain`, target and source path checks, the CLI error line and the source loader. Control characters and an explicit list of invisible or reordering characters are escaped (`\u{...}`) when printed and refused in a target or source path: soft hyphen, U+034F, U+061C, Hangul and Khmer fillers, Mongolian variation selectors, zero-width and directional marks, line and paragraph separators (U+2028, U+2029), bidirectional embedding, override and isolate controls, U+2060 to U+206F, the braille blank (U+2800), variation selectors, the byte order mark, interlinear annotation, tag characters (U+E0000 to U+E007F) and variation selector supplements. Rust's standard library has no Unicode general category, so this is a list, not a category test. A backslash is printed as `\\`, so a name that holds the two characters `\` and `n` cannot pass for the escape of a newline. Text is escaped once, where it is printed: refusals, plan blockers, `doctor` rows and apply messages carry the raw text, and the last step that prints them escapes it. A second pass would double each backslash.
17. **Digests.** Each source file or directory is hashed once per resolve call, however many values name it. The cache for a directory is keyed by the trusted root too, because entry links must stay inside each root that reaches it.
18. **Arguments.** A command-line argument that is not valid UTF-8 is a usage error (exit 2), not a panic.

## Source roots and excludes

A live checkout holds runtime trees that the manager's own links put there: plugin checkouts with their own `.git`, virtual environments, `node_modules`, caches. The loader refuses or chokes on them. The bundle that the profile names can declare which parts of `--root` are sources.

```toml
[sources]
roots = ["home", "dfm"]
exclude = ["home/.config/tmux/plugins", "**/__pycache__", "**/.venv", "**/node_modules"]
```

1. **Absent table.** Without `[sources]` the loader reads all of `--root`.
2. **Where it may appear.** Only in the bundle that the profile names. An extended bundle that declares it is `E_MANIFEST_INVALID`. The table is closed: other keys are `E_FIELD_UNKNOWN`. `roots` is required and not empty. `exclude` is optional. Each list holds at most 1,000 entries, and each entry is at most 4,096 bytes (`E_MANIFEST_INVALID`).
3. **Roots.** Each root is a root-relative path with no `..`, no empty component, no wildcard and no leading `/`. It must exist as a real directory, and no component of it may be a link. A missing or non-directory root is `E_MANIFEST_INVALID`. A link in a root is `E_SOURCE_ESCAPE`. A root inside another root is read once. A root with a `.git` component is `E_MANIFEST_INVALID`. So is an exclude that matches the bundle directory or one above it. So is a root that equals an exclude match or lies below one (a lone `**` excludes every root).
4. **Excludes.** Each exclude is a glob over the root-relative path, anchored at `--root` (there is no gitignore-style matching of a bare name). `*` and `?` match within one path component. A component that is exactly `**` matches zero or more components. `**` inside a longer component is `E_MANIFEST_INVALID`. Matching ignores case, as source lookup does. A pattern that matches a directory excludes its whole subtree.
5. **What is read.** Every entry under a root, and the files and links that sit directly in the directory that holds the bundle file. Subdirectories of that directory are read only when a root holds them. The loader checks an exclude before it lists, opens or counts the entry. An excluded directory is not listed and an excluded file is not opened.
6. **Excluded entries are invisible, and counted.** A directory source (a `link` to a directory, a fragment directory, a distribution root) sees only the loaded entries. An excluded entry inside it is not part of the content identity of that directory.

   Exclusion affects hashing only, never containment. The loader still records an excluded entry that is a symlink with its target, and the resolver checks that target like any other link in the directory source (`E_SOURCE_ESCAPE`). An excluded directory is not listed, so a link inside it is not seen at plan time.

   At apply time the engine lists a directory source that has excluded entries and checks every link in it, at any depth, against the directory source itself (not the module root, not `--root`). A target must be relative and may climb only with leading `..` components, no more than the depth of the link, because a `..` after a name may start from a link. The check fails closed. A cut listing, a directory or entry that cannot be examined, a name that is not UTF-8, more than 1,000,000 entries and nesting deeper than 64 are refused, and an escape is `E_SOURCE_ESCAPE`.

   Plan holds such a directory to the same rule for every link it can see, loaded or excluded, with the same function (`dfm_model::resolve::target_stays_inside`). A link to a sibling in the module root, which plan accepts for a directory with no excluded entry, is `E_SOURCE_ESCAPE` here, and so is `sub/../keep`. A link inside an excluded directory is the one case plan cannot predict: apply still refuses it when it is absolute or climbs out, although the plan passed (for example `.venv/bin/python -> /usr/bin/python3`). The plan prints a note about it.

   A directory with no excluded entry is not walked at apply. So plan also refuses a link in it that leads to a directory which holds an excluded directory (`E_SOURCE_ESCAPE`, "holds an excluded directory"), because the links inside that directory are neither listed nor walked. An excluded file or link there does not matter. Two excluded links whose names differ only by case are both checked. The loader reads the target of an excluded link like any other: it must be UTF-8 and hold no control character.

   The loader records each excluded entry that exists (more than 100,000 is `E_LIMIT_EXCEEDED`). Under each operation whose directory source holds some, the plan prints `note: contains N excluded entries, not hashed` and a second note that apply checks the links inside excluded entries. The JSON operation carries `excluded = N`, and the count is inside the plan digest. A directory link still publishes the excluded content on apply. The note makes that visible and the owner accepts it.
7. **Escape.** A path that leaves the declared roots, or that matches an exclude, is `E_SOURCE_ESCAPE`. A directory source must be a root or lie under one. A directory above a root, the bundle directory and a subdirectory beside the bundle are `E_SOURCE_ESCAPE`, because only part of them was loaded. This covers the profile, the bundles, the module manifests, resource sources, assembler bodies, fragment sources and templates, and every link hop between them. The message names the path. The fix text names the declared roots or the matching pattern. The bundle, module and profile manifests must lie in a root or directly in the bundle directory.
8. **`.git`.** A root may not name `.git`. A `.git` below a root is `E_SOURCE_UNTRUSTED`, unless an exclude matches it or a directory above it. The loader skips without an error the top-level `.git` of `--root`, and a `.git` that sits directly in the bundle directory when no root holds that directory (that directory is read without descending).
9. **Cap.** The 20,000-entry cap counts the loaded set only. When it is exceeded, the message lists the three directories with the most direct entries, counted by a second pass that lists directories and opens no file. The count stops at 1,000,000 entries and the message then says "at least".
10. **Empty directories.** The loader records every directory it walks, also one with no loaded entry (an empty one, or one whose children are all excluded). A directory source that is empty is a directory and plans as a directory link. A declared root with nothing loaded below it is a directory too. The loader refuses two names in one directory that differ only by case (`E_SOURCE_UNTRUSTED`), because the snapshot indexes directories by folded path. A directory entry (`dir` class, no value) is part of the content identity of a directory source and of the source tree digest, so adding an empty subdirectory changes both.
11. **Digest.** The source tree digest covers exactly the loaded set, directories included. The bundle file is part of the loaded set, so a change to `roots` or `exclude` changes the digest. A change to an excluded file does not.
12. **One loader.** Every command that reads sources (`explain`, `plan`, `doctor`, `apply` and its scoped forms, and `sync` on its staged tree) loads through `source_fs::load_scoped`.
13. **Same bundle.** The loader finds the bundle by joining the profile directory and `bundle` and collapsing `..` as text. The resolver follows links. After it reads the bundle chain, the resolver requires that the loaded `[sources]` is the one declared by the bundle it resolved. Otherwise it is `E_MANIFEST_INVALID` and names both files. This also refuses the case where the loader found no `[sources]` and the resolved bundle declares one.

### Directory links

An `fs-link/v1` resource whose `source` is a directory must declare `directory = true` in its value (DFM-55). That is the explicit directory claim: the planner treats the resource as one link to a directory. Without the flag a directory source is `E_MANIFEST_INVALID`, and the fix text names the flag. Containment covers every entry at any depth. A link that reaches another directory is followed into that directory's entries too, each directory once for the whole composition, so `D/ln -> ../x` with `x/esc -> /etc` is `E_SOURCE_ESCAPE`. The flag on a file source has no effect. `skills/v1` distribution entries are directories by design and need no flag. Any other adapter refuses a directory source.

## Native precedence

DESIGN.md section 5 requires native precedence to be visible per value. The resolver reads it from the authored document, not from a manifest field. An `fs-link/v1` source that is a native config is scanned for include directives. The CLI registers a Git parser: `[include]` and `[includeIf "<condition>"]` sections, with the `path` key on its own line or on the header line. The value is read as Git reads it: double quotes group text, a backslash escapes the next character, and an unquoted `#` or `;` starts a comment. A source that is not valid UTF-8 is `E_MANIFEST_INVALID`, because its includes cannot be read.

The result is `Resolved.includes`: for each such document, the includes in file order, each with its condition and the resource that declares the included file (matched by output path). A path `~/x` names the output `x`. A relative path is matched against the directory of the including document's output, as Git does, with `.` and `..` applied; one that climbs above HOME matches nothing. An absolute path or `~user/x` matches no resource, so it is reported as undeclared. A file included twice appears at each position.

`explain` prints, for every native fragment, each position and condition, the ordered siblings, the adapter's ordering rule (kept on the fragment's resource only), and for each value the other fragments that also set it. For a Git config the rule is "later include entries override earlier ones for single-valued keys". Only values set in more than one fragment depend on the order.

**What is not modelled.** The authored document's own keys, and where they sit relative to its include lines, are not read. Git applies a key in the base file before or after an include depending on position, so a value the base file also sets can win or lose against a fragment in a way `explain` does not show. A native document that no authored file includes reports that the application decides, and no order is invented. The manager cannot validate the resulting native file, so a protected setting is not enforceable against a fragment. Native-setting probes are not built ([docs/adapters.md](adapters.md), "Not built").

## Fragment injection

The direct-placement exception (rule 14) lets any selected module put a pattern-matching file into another module's assembled output and choose its position by file name. The owner does not opt in, and no owner-side opt-in (in the style of `policy.extensions`) exists. `explain` therefore lists, for each `text-fragments/v1` resource, every supplier with its position, module and declaring file, so injection is visible. Two assemblers whose outputs land in each other's directories both resolve, because each output matches the other's pattern. The planner rejects that loop as `E_PLAN_CYCLE` ([docs/planner.md](planner.md), rule 8).

## Not enforced here

- **Public closure must not reach an external source** (architecture section 6 item 5). **The resolver deviates from that rule.** Schema 1 labels no bundle public or external, and the source lock (`dotfiles-manager.lock`, [docs/sync.md](sync.md)) records no such class either. The resolver enforces what it can see: a bundle cannot reach modules outside its own directory, `extends` cannot form a cycle, and the public fixture resolves with no private file present. Nothing stops a public bundle from extending a private one.
- **Unicode normalization.** Output paths and source names are compared after case folding only. Two names that differ only by normalization form (NFC against NFD) are not detected as one name, and APFS treats them as one. The planner closes this for claimed paths by refusing non-ASCII names ([docs/planner.md](planner.md), rule 1). Source names are not covered. Closing it needs a normalization dependency, which the architecture has not accepted.
- **Tree rewritten during a load.** `O_NOFOLLOW` covers the final path component only. A parent directory replaced by a link after it was listed would still be followed. The loader also reads the profile and the bundle (to find `[sources]`) before it reads the tree. It assumes nobody rewrites the tree while it runs.
- **Directories reached through a link in a directory source.** The tree digest of a directory source covers its own entries and the link text, not the directories its links lead to. Apply does not follow those links, so a change in a linked directory between plan and apply (for example `x/esc` swapped to `/etc` behind `D/ln -> ../x`) is not detected. Closing it needs a plan digest that covers followed directories.
- **Real symlinks at apply time.** The resolver decides containment on a snapshot. Apply checks the live source again with descriptor-relative operations ([docs/apply.md](apply.md), "Link source").
- **Secret redaction depends on discipline.** Errors never copy a value. `explain` redacts values of `secret_values` resources. Nothing else prints resolved values, but `Debug` on a `ResolvedResource` shows them.
