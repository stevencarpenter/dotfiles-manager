# Bootstrap, binding and build controls

Task: DFM-14. This document records what the first implementation does and where it differs from [docs/architecture.md](architecture.md) (the contract). The contract wins where this document is silent.

## What exists

| Part | Location |
| --- | --- |
| Workspace crates `dfm-model` (pure data and rules), `dfm-platform-macos` (HOME, paths, platform check), `dfm-cli` (binary `dotfiles-manager`) | `crates/` |
| POSIX sh bootstrap and build-controls checker | `scripts/bootstrap.sh` |
| Shared checker fixtures (115 cases) | `tests/fixtures/build-controls/` |

`ports` and `adapters` are not created yet. `engine` holds state persistence ([docs/state.md](state.md)).

## CLI

```
dotfiles-manager --version | --help
dotfiles-manager bind --profile <file> --machine-id <id>
dotfiles-manager binding
dotfiles-manager state check
dotfiles-manager self-check --build-controls <staged tree> | --fixture-dir <dir>
```

- `bind` records the canonical profile path and a machine identity in `~/.config/dotfiles-manager/machine.toml` (schema 1, mode 0600, directory 0700). Nothing is inferred: both flags are required.
- `bind` also creates the state directory (see [docs/state.md](state.md)) before it writes the binding, and takes the manager lock. A concurrent second `bind` can therefore exit 3 with `E_LOCKED` instead of `already bound`. A second `bind` with the same identity succeeds without a write, unless `state/salt` is unusable, which is `E_STORAGE_INVALID` (exit 3). A different profile or machine id exits 3 with `E_REBIND_UNSUPPORTED`. There is no force flag. Rebinding is an ownership migration and is not implemented.
- `bind` refuses a profile that is not a regular file of at most 1 MiB that parses as TOML with a top-level `schema` key that is the integer 1 (a missing or non-integer `schema` is `E_PROFILE_INVALID`, another integer is `E_SCHEMA_UNSUPPORTED`, both exit 3 and both before any write). The resolver checks the rest in a later task. A binding that cannot be read or is wrong is never overwritten. Manual recovery: inspect `~/.config/dotfiles-manager/machine.toml`, and if the machine really should be rebound or the file is damaged, remove that file yourself; no command does it.
- The binding is opened without following symlinks and must be a regular file owned by the current user with mode 0600; anything else is `E_BINDING_INVALID`. The config directory is synced after the file is linked.
- The binding file is published with a temporary file, `fsync` and an exclusive rename (`RENAME_EXCL`), which never replaces an existing file. Concurrent binds leave one identity.
- Nothing applies configuration. Installation and `bind` only write the files named here.
- Errors are one line, at most 512 characters, with control characters escaped. Exit codes follow the contract (0, 1, 2, 3, 4, 5, 130, 143). Exit 3 is only for refusals before any write. An I/O failure while writing the binding or the output is `E_IO_FAILED` with exit 1. Codes 4 and 5 are defined and tested for precedence but no command produces them yet. Only `apply` produces 130 and 143: it installs a SIGINT and SIGTERM handler after it takes the lock (docs/apply.md, Signals). Every other command installs no signal handler.
- Isolation overrides (`--home`, `DFM_HOME`, `DFM_BINDING`, `DFM_PLATFORM`) compile only with the cargo feature `test-isolation`. Those builds print `isolated: true` and append `test-isolation` to `--version`. The installed release binary ignores them (tested). The feature is switched on only by `--features dfm-cli/test-isolation` (the gate does this); no self dev-dependency enables it, and a gate test builds every release target without the flag and checks `--version`. `rust-toolchain.toml` in the repository lists `rustfmt` and `clippy`; the checker allows exactly those two components besides the pinned channel.

## Source and build identity

- A source identity is the git commit plus the recomputed tree digest. `bootstrap.sh install` requires `--commit <full lowercase object id>` (40 digits, or 64 in a sha256 repository) and builds `git archive` of exactly that commit; `HEAD` and uncommitted files play no part. Git runs with the scrubbed environment from the contract. The script runs no `git status`, because that would run filters configured in the repository (tested). `install` also refuses a source checkout that has a non-empty `.git/info/attributes`, a `core.attributesFile` setting or any `filter.*` setting with `E_SOURCE_UNTRUSTED` (exit 3, before any change). `git archive` would otherwise apply those checkout-local attributes (`export-ignore`, `export-subst`) or run the filter commands, and the staged tree could differ from the pinned commit (tested). Attributes committed in the pinned tree remain part of that commit. The script pins `core.autocrlf=false` and `core.eol=lf` on the git command line, which outranks the checkout's config, so a checkout-local line-ending setting cannot rewrite the staged files. Only the `core.autocrlf` pin is tested (with a stand-in `cargo fetch` that looks for a carriage return in the staged manifest): with git 2.54 a checkout's `core.eol` alone does not change `git archive` output, so the `core.eol` pin is defence for other git versions and is not tested. The configuration is read first. A failed `git config` call (exit above 1) or `git rev-parse` call in these checks refuses with `E_SOURCE_UNTRUSTED`; an empty answer from a failed call never counts as "nothing found" (tested with an `include.path` that names a directory, which fails the `git config` call, and with a source directory that is not a git checkout, which passes the `git config` call and fails the `git rev-parse` call). Other checkout-local settings that change `git archive` output only through attributes the pinned commit itself commits (for example `core.abbrev` with a committed `export-subst`) are not pinned; this repository commits no `export-subst`.
- The build input is `git archive <commit>` of the verified `--commit` (not whatever `HEAD` is). Git runs with `GIT_NO_REPLACE_OBJECTS=1` and `core.useReplaceRefs=false`, so a `refs/replace` entry cannot swap the content (tested). `--commit` must be a full lowercase hex object id (40 digits, or 64 in a sha256 repository whose object format matches). Abbreviations, uppercase, refs, tags, `HEAD`, `^`, `~`, `@{}`, option-like values and whitespace are refused with `E_SOURCE_UNTRUSTED` before any git call (tested for 19 forms). git resolves `<id>^{commit}` after `--end-of-options`, and the resolved id must equal the pin. The pin is not read from the lock: this implementation's lock carries the toolchain fields only.
- `--source` is a local checkout (a working tree or a bare repository), an `https://` or `file://` URL, or absent. Absent means the canonical origin, `https://github.com/stevencarpenter/dotfiles-manager.git` (the `ORIGIN` constant in the script). A URL is cloned bare, with `transfer.fsckObjects=true` and the scrubbed git environment, into `~/.cache/dotfiles-manager/build/source.git`, after every local check has passed (command path, binding, directory hierarchy) and before `git archive`. The pinned commit is then read from the clone with exactly the checks a local checkout gets: configuration, attributes, object format, `rev-parse` of the full id, the script identity and the toolchain hint. No working tree is written, so there is no checkout head that could differ from the pin: `git archive <commit>` reads the commit object itself. A commit the origin does not have, or an origin that cannot be cloned, is refused with `E_SOURCE_UNTRUSTED` (exit 3) and the exit trap removes the clone with the build directory (tested with a `file://` origin, offline). After a successful build the clone goes with the build directory; `uninstall` removes it with the build directory too (tested). The network is used only in this clone step and only when the owner named a URL or no source. The gate's install tests use a local checkout and a `file://` origin only; the `https://` clone of the canonical origin is not run by any test.
- Script identity. Every command accepts `--expect-sha256 <64 lowercase hex>`. The script digests the file it runs from (`$0`, made absolute) before it does anything else, before the platform, HOME, tools or source are looked at, and refuses with `E_SOURCE_UNTRUSTED` (exit 3) when the digest differs (tested with an edited copy run from its own path, and with a wrong value given to `install`, which is refused before the unsupported platform is). `install` also requires the running file to be byte-identical to `scripts/bootstrap.sh` of the pinned commit, read with `git cat-file` from the source after the commit id resolved: a stale, edited or foreign copy of the script cannot build a commit it does not belong to, and a commit without the script is refused (tested, nothing written). The options considered: (a) a digest recorded in `dotfiles-manager.lock` or a sibling file in the same commit protects against a corrupted or stale copy only, since the file travels with the script, and needs a gate step to keep it current on every script change; (b) the committed blob of the pinned commit protects against the same, is current by construction (the commit is the record) and costs one `git cat-file`; (c) a value the owner holds out of band (`--expect-sha256`, contract section 12 item 3.1) is the only one that protects against a script and commit pair the owner did not pin, for example a script copied from another machine with the wrong commit id. The implementation does (b) always and (c) when given; nothing switches (b) off. What no self-check can do: a hostile script can skip its own checks and print any digest. The owner's anchors stay the commit id and, when the copy of the script is not trusted, `shasum -a 256 bootstrap.sh` run by hand against the recorded value before the script runs. That hand check is the remaining manual step; it is no longer needed for the drift case (a script that does not match its commit), which the script refuses itself.

- The script sets `DFM_BUILD_COMMIT` for the build. `--version` prints `dotfiles-manager <semver> (commit <sha>)`. The installed directory is `versions/<semver>-<first 12 of commit>`.
- The binary SHA-256 is printed after install as a record only. Builds are not claimed to be reproducible.
- The owner obtains the script file and the commit id out of band, as in contract section 12 item 3.1; a script cannot fetch itself. From there the script does the rest: `sh bootstrap.sh install --commit <sha> [--expect-sha256 <hex>]` clones the canonical origin at the commit, checks that it carries this exact script, builds and installs. The manual `git clone`, `git rev-parse HEAD` and `shasum` steps of the earlier procedure are gone; a local `--source <checkout>` keeps working and is what the gate tests use.

## Running the script

Start it as `/bin/sh scripts/bootstrap.sh <command> ...` (or `/bin/sh bootstrap.sh ...` for a copy of the file). Not with `env -i`: that clears `HOME`, which must equal the password-database home, so the script refuses with `E_HOME_MISMATCH`. Not through `curl | sh`: the script re-executes and digests itself by its path (`$0`), which a pipe does not have; that path stays unsupported. The script re-executes itself under `env -i` with a fixed `PATH` and the caller's `HOME`, so exported shell functions of any name (`BASH_FUNC_*`, for example a forged `cut`, `awk`, `[` or `test`), `PERL5LIB`/`PERL5OPT` (`shasum` is perl), `CDPATH` and `ENV` do not change what is checked (tested). The marker that says "already scrubbed" is the first argument `--dfm-scrubbed`, not an environment variable. A caller can pass that argument itself, so the child checks that its environment holds only `PATH`, `HOME`, the shell's own `PWD`/`OLDPWD`/`SHLVL`/`_` and, in test mode, the `DFM_TEST_*` hooks. Any other name is refused with `E_ENV_UNEXPECTED` (exit 3), whatever it is called. Before the scrub the script uses only `case`, `exec`, `shift` and absolute-path commands, so an imported function cannot intercept its tests (tested with functions named `[` and `test`; the test also proves the allowlist, not only the `PATH` check, by passing the exact `PATH` and a clean-environment control). The `DFM_TEST_*` values are forwarded only when `DFM_BOOTSTRAP_TEST=1`. Relative `--source` and `--dir` values are made absolute first.

An inherited `SHELLOPTS` or `PS4` (xtrace with command substitution, or `noexec`) takes effect before the first line of the script and is outside its control. `noexec` makes `/bin/sh` skip the whole file and exit 0. A run that did not print its final line did not finish: `bootstrap: done` for install, `removed the installed manager` for uninstall, `build controls ok` for `check-controls`.

## Install, upgrade, rollback, removal

1. Place the exact pinned toolchain as a real directory (not a symlink) at `~/.local/share/dotfiles-manager/toolchains/<version>/`. `~/.local/share/dotfiles-manager` must be a real, user-owned directory first. The repository carries `dotfiles-manager.lock` with the digest of the toolchain on the authoring device (aarch64 macOS, `1.98.1`). On that device run `mkdir -p ~/.local/share/dotfiles-manager/toolchains` and check that `~/.local/share/dotfiles-manager/toolchains/1.98.1` does not exist (`[ ! -e ~/.local/share/dotfiles-manager/toolchains/1.98.1 ]`), because `cp -R` into an existing directory nests the copy one level down. Then run `cp -Rp ~/.rustup/toolchains/1.98.1-aarch64-apple-darwin ~/.local/share/dotfiles-manager/toolchains/1.98.1` as the current user (not with `sudo`, because an entry owned by another user is refused), then `sh scripts/bootstrap.sh toolchain-digest --dir ~/.local/share/dotfiles-manager/toolchains/1.98.1`. The printed value must equal `toolchain_tree_sha256` in the lock before `install`. If the copy was nested anyway, install refuses with `E_TOOLCHAIN_MISMATCH` and names the extra directory (`toolchains/1.98.1/1.98.1-aarch64-apple-darwin`); remove `toolchains/1.98.1` and copy again. The digest is device-specific: another device, such as the M3, may need its own lock. To change a lock, compute the digest with the same command, review it, then write `[manager] toolchain` and `toolchain_tree_sha256` into `dotfiles-manager.lock` in the commit to build.
2. `sh scripts/bootstrap.sh install --commit <sha> [--source <checkout or URL>] [--expect-sha256 <hex>]`. Order: the script's own digest against `--expect-sha256` when given, platform, HOME (the password-database home must equal `$HOME`; it is refused with `E_HOME_MISMATCH` if it contains ASCII whitespace or control characters, a C1 control U+0080 to U+009F, or Unicode White_Space such as U+00A0, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F or U+3000, the same set as `valid_home` in the CLI, matched on the UTF-8 bytes), Command Line Tools probe (before any git call, because `/usr/bin/git` is the Command Line Tools shim; the probe runs `xcode-select -p` and checks that a `clang` file exists under the printed path, in `usr/bin` or in Xcode's default toolchain, and never runs a shim; a missing install is refused with `E_PREREQ_MISSING` and the instruction to run `xcode-select --install`, and the script never starts the installer or polls), a refusal when the script file or a local `--source` lies inside `~/.cache/dotfiles-manager/build`, which `install` resets (`E_PREREQ_MISSING`, tested with a copy of the script run from there), source identity for a local checkout (for a URL these checks run after the clone, below), script identity against the pinned commit, toolchain presence (the pin is read from `[manager].toolchain` with the same restricted grammar the staged check uses: leading whitespace trimmed, only the `[manager]` table), the command path (an existing file or foreign symlink at `~/.local/bin/dotfiles-manager`, or a `current` or `current.new` that is not a symlink, is refused, never replaced), the binding check (below), the cache and data directory check (below), the bare clone of a URL source into the build directory followed by the source and script identity checks on it, stage, build controls, then `cargo fetch --locked`, `cargo build --release --locked --offline` with an empty constructed environment, `self-check --fixture-dir` against a copy of the existing `machine.toml` (a new binary that cannot read the current binding never becomes current), and install. No cargo, rustc or rustup process starts before the controls pass.
3. Upgrade is the same command with a newer commit. The new version directory is written first. The command link is created first when it is absent (an existing link already resolves through `current` and is not rewritten), then `current` flips by one atomic rename of a symlink, after the new binary passed `self-check`. After the flip only the read-back and the cleanup remain, so a failing command-link operation cannot leave a new active version without a completion marker. A failed build or check leaves the previous version active. Old version directories stay. State is not migrated here (state upgrade belongs to a later task).
4. Rollback: point `current` at the previous `versions/<name>` (`ln -s versions/<name> current.new && mv -fh current.new current`).
5. `sh scripts/bootstrap.sh uninstall` first refuses (`E_PREREQ_MISSING`, exit 3, before any removal) if `current` or `current.new` exists and is not a symlink, because the installer creates only symlinks there, or if `~/.local/bin` is a symlink, is not a directory, or fails the owner and mode rule below. It then removes the PATH link (only if it points at this manager), `versions/`, `current`, the build directories and `~/.cache/dotfiles-manager/build`, then the data and cache directories if they are empty. It leaves `~/.local/bin` (the installer does not own it), toolchains, state, the binding and anything else in the cache root.

The running manager is never replaced in place, so an upgrade does not depend on the executable it replaces. Nothing that is in use during a run is retired by it: the interpreter is `/bin/sh`, which the script never writes; the script file is read by its path and never written, moved or removed (a copy inside the build directory is refused before the reset); a local source checkout is only read (`git config`, `git rev-parse`, `git cat-file`, `git archive`), and a checkout inside the build directory is refused the same way; a URL clone lives in the build directory and is removed only after the build and the swap are done, or by the exit trap of a run that did not finish; the previous version's binary stays in `versions/<name>`, since the swap replaces only the `current` symlink and `uninstall` is the only command that removes version directories. Recovery after an interrupted run is a second `install` with the same arguments: it resets the build directory first (tested with a stale, read-only one) and either version directory that exists is left usable. The install needs only POSIX sh, system tools in `/usr/bin:/bin:/usr/sbin:/sbin`, Git, Command Line Tools and the placed toolchain.

## Build controls and the restricted grammar

`bootstrap.sh check-controls --source <tree>` and `dotfiles-manager self-check --build-controls <tree>` implement the same checks: staged tree, then toolchain tree digest, then ancestors. Both exit 3 on refusal and print the first failing control. The differential test runs both over `tests/fixtures/build-controls/cases/*` and requires the same result.

The checker reads only: comments; `[a.b]` and `[[a.b]]` headers with bare names; `key = value` with a bare key and a single-line string without escapes, boolean, integer, array or inline table of those. It refuses everything else, including multi-line values, dotted or quoted keys, floats and dates, non-ASCII bytes, CR, and files over 1 MiB.

Rules: names are matched case-insensitively, and two paths that differ only in case are refused (the macOS file system folds case); duplicate tables, keys and inline keys are refused; no `.cargo/config.toml` or `.cargo/config` at any level; no `rust-toolchain` file; every `rust-toolchain.toml` must contain only `channel` equal to the lock pin; every `path`, `members`, `exclude`, `default-members`, `build` and `workspace` string must stay inside the root (a `..` after a normal component is refused); `git`, `registry` and unlisted dependency keys are refused (the tables `dependencies`, `dev-dependencies`, `build-dependencies` and the underscore spellings `dev_dependencies` and `build_dependencies`, also under `target.<name>.`, are all treated as dependency tables); `[replace]` is refused; `[patch]` is allowed only for `crates-io`; `Cargo.lock` lines must be recognised and any `source` must be crates.io; symlinks and special files in the tree are refused; the root `Cargo.toml` must declare `[workspace]` (otherwise a `Cargo.toml` planted in an ancestor could adopt it and add `[patch]` tables); an ancestor of the build directory that cannot be searched is refused with `E_BUILD_CONFIG` instead of being treated as free of config.

The checker and `toolchain-digest` fail closed: an unreadable entry, a failed hash, a bad symlink (including a target that ends in a newline, which the script reads with `readlink -n` so that no byte is dropped) or a tree without a regular file (empty, or only symlinks; both the script and `self-check --build-controls` refuse it) is a refusal, never a digest of the readable part. After the build the script requires the binary to report exactly `dotfiles-manager <digits.dots> (commit <the verified commit>)` before it names the install directory.

## Differences from the contract

1. **Staged-tree refusals use `E_SOURCE_UNTRUSTED`.** Contract section 8 item 3 says so for a staged `.cargo/config*`, but section 8 item 3a lists "configuration" under `E_BUILD_CONFIG`. This implementation follows item 3: `E_BUILD_CONFIG` is for the build directory and its ancestors only.
2. **Stricter than the contract:** any symlink in the staged tree is refused (the contract allows symlinks that stay inside the root); `[replace]` is refused outright; Cargo manifests may not use multi-line arrays or strings.
3. **Binding location.** The binding is at `~/.config/dotfiles-manager/machine.toml` as contract section 5 says, not in the state directory. Durable binding storage in state belongs to DFM-17 (C07 is not claimed).
4. **New error codes** beyond the contract list: `E_IO_FAILED`, `E_PLATFORM_UNSUPPORTED`, `E_REBIND_UNSUPPORTED`, `E_BINDING_INVALID`, `E_PROFILE_INVALID`, `E_USAGE`, `E_PREREQ_MISSING` (script only).
5. **Tree digest framing.** Each entry is `path NUL class NUL value LF`; the contract does not fix the terminator. The class `exec` means the owner execute bit is set.
6. **Test hooks in the script.** With `DFM_BOOTSTRAP_TEST=1` the script reads `DFM_TEST_HOME`, `DFM_TEST_OS` and `DFM_TEST_ARCH` in place of `dscl` and `uname`, `DFM_TEST_CLT=missing` to simulate missing tools, and `DFM_TEST_UID=<uid>` to name the owner that the directory-hierarchy, toolchain, and uninstall HOME owner checks expect (a test cannot create a file owned by another user; the binding and config-directory checks mirror the CLI and always use the real user id), `DFM_TEST_BEFORE_COPY=<script>`, `DFM_TEST_BEFORE_SWAP=<script>` and `DFM_TEST_AFTER_SWAP=<script>` to run a script right before the binding copy and right before and after the final swap (so a test can create the race the re-check guards against). They exist so tests can use a temporary HOME. A caller who can set them already controls the user's environment; they are not an integrity boundary. Without the variable the script uses the password database, and a temporary HOME gives `E_HOME_MISMATCH` (tested).
7. **Cache location.** `cache_dir()` is `~/.cache/dotfiles-manager`; the contract leaves it open. The script and `dfm-platform-macos` hard-code the same literal and a test compares them.
8. **Signals.** Bootstrap commands do not catch SIGINT or SIGTERM. `apply` does (DFM-47).
9. **Command Line Tools.** Same as the contract after its update (owner-delegated decision, 2026-10-10): a missing install is refused, not installed or polled for.
10. **Fetch.** `cargo fetch --locked` runs with crates.io as the only registry in an empty `CARGO_HOME`. The install test therefore needs network access.
11. **Bootstrap provenance.** Contract section 12 item 3.1 has the owner clone the pinned commit and verify the script checksum before the script runs. Here the script itself clones the origin (bare, `transfer.fsckObjects=true`, scrubbed git environment) and checks that the pinned commit carries the script that runs; the owner's out-of-band checksum is given as `--expect-sha256` and is optional. The clone is bare, so "verify the checkout head" becomes "resolve the full id and `git archive` that commit": no head exists to drift. `file://` URLs are accepted besides `https://` so the gate can test the clone path offline; the canonical `https://` origin is the default when `--source` is absent.

## Accepted risks

- After the controls pass, the staged tree is made read-only (`chmod -R a-w`) and the toolchain digest is checked again immediately before `cargo fetch`. A process running as the same user can still change permissions or files between those steps and the build, or swap a directory for a symlink between the hierarchy check and its use. The contract's trust boundary is the user account, so this is accepted and not closable without a sandbox. Build scripts and procedural macros already run as the user (contract section 8, known exception).

- The early pin hint is looser than the staged check: it applies no 1 MiB limit and no ASCII filter. Both refuse `[[manager]]` (an array of tables). The staged check is authoritative and runs before any build.
- An install that ends without finishing (a refusal or failure after the build directory exists, SIGINT or SIGTERM) removes the build directory and the build homes, each only if the directory check for that tree passes (tested per tree), and prints what it left. SIGINT and SIGTERM end the script with 130 and 143 after the cleanup (tested with a stand-in `cargo`). SIGKILL and any signal the script does not trap leave them in place, together with the staging leftovers (hidden `.dotfiles-manager-link.XXXXXX` directories in `~/.local/bin`, `dotfiles-manager.new.XXXXXX` files in a version directory). The next `install` and `uninstall` remove the build directory and homes; neither cleans the staging leftovers.
- A symlinked `~/.cache`, `~/.local`, `~/.local/bin`, `~/.local/share` or `toolchains` (also `versions`, `cargo-home`, `rustup-home` and `build-home`) below the data directory is refused by policy, even when the link is the owner's own arrangement.
- The script's self-checks (`--expect-sha256` and the committed-blob comparison) are evidence of a matching script, not of an honest one: a modified script can skip them. The build-directory guard compares literal paths, not resolved ones; a script or source reached through a symlink into the build directory is not caught (the owner's own arrangement, same as the symlink policy above).
- A URL install leaves a bare clone of the whole history in the build directory until the run ends; a run killed with SIGKILL leaves it there with the other build leftovers, and the next `install` or `uninstall` removes it.

## Known gaps and deviations kept for later

- **cargo-deny, cargo-audit and cargo-vet are not wired in.** There is no `deny.toml`; the license allowlist is an owner decision. Follow-up task title: "chore(gate): add cargo-deny and cargo-audit with an owner-approved license allowlist".
- **Prints only the first failed control.** Contract section 8 item 3a says `self-check --build-controls` prints each failed control. Both checkers stop at the first failure.
- `bounded()` escapes control characters but not bidirectional-override characters.
- `dfm-cli` performs file I/O (binding read/write, tree walk) directly. The contract puts file access behind an `Fs` port in `engine`; no `ports` or `engine` crate exists yet.
- `dfm-model` hard-codes the `macos`/`aarch64` platform in the binding rules. The contract keeps platform names out of `model`.
- `Platform::with_home` is `pub` and not feature-gated; only `dfm-cli` calls it, and only in a `test-isolation` build.

## Binding checks before the build

Install refuses before any mutation (the first mutation is the reset of `cargo-home`, `rustup-home` and `build-home`; the scratch build directory before it is removed on exit, and build-control refusals before it exit 3; `E_BINDING_INVALID`, exit 3 for the file-type, mode and owner checks, which use the CLI's code and exit; a content parse failure found by the pre-flip self-check exits 1 in the script, while the CLI refuses the same file with `E_BINDING_INVALID`) unless an existing `~/.config/dotfiles-manager/machine.toml` is a regular file (not a symlink or FIFO), mode 0600, owned by the current user, with exactly one hard link (a second link is `E_BINDING_INVALID`, exit 3, because the CLI refuses it and `cp -p` would hide it): the same rules the CLI applies when it reads the binding. The pre-flip `self-check --fixture-dir` then runs on a `cp -p` copy of that exact file. The CLI opens the binding relative to the verified config directory descriptor with `O_NOFOLLOW | O_NONBLOCK`, so a FIFO is refused instead of blocking, and it forces mode 0600 after creating the file whatever the umask. The directory chain is checked with the binding: HOME, `~/.config` and `~/.config/dotfiles-manager` must each be a real directory (a symlink is not followed, except that HOME is resolved first and its target is checked, as the CLI does), owned by the current user and not writable by group or others, the rules `open_config` applies. A missing component is allowed because the CLI creates it. A violation is `E_PREREQ_MISSING`, exit 3, naming the component. The binding and its directory chain are checked at the start (before any build artefact exists), again immediately before the `cp -p`, and again before the swap (an unusable binding then stops the swap with exit 1, because the binary was already copied into `versions/`). The command path and `current` are checked at the start and again right before the swap: `current` and `current.new` must each be absent or a symlink (tested without following links), and the command path absent or already this manager's link (`E_PREREQ_MISSING`; exit 3 at the start, exit 1 at the check before the swap). After the swap both links are read back (`current` -> `versions/<name>`, the command path -> `current/dotfiles-manager`); if either differs the script exits 1 with "swap did not take effect" and does not print `bootstrap: done` (tested with an after-swap hook). The directory checks run once more after the swap. The swap has happened by then, so a failure there is exit 1, not a refusal with exit 3: the script removes the build directory and the build homes whose own check passes, names what it left, and says that the new version is current. The command link is staged as a symlink inside a directory that `mktemp -d` creates in `~/.local/bin`, then renamed into place, so no pre-existing name there (including `dotfiles-manager.new`) is read, followed or removed. The engine checks owner and mode on the open descriptor and tests the owner rule with a different user id (`permissions_and_owners_are_checked_not_repaired`); no end-to-end test uses a file owned by another user.

Directory hierarchy check. Before `install` removes or changes anything, and before `uninstall` removes anything, the script walks `~/.cache/dotfiles-manager/build` and each of `~/.local/share/dotfiles-manager/{versions,cargo-home,rustup-home,build-home}` from HOME down without following symlinks. A component that is a symlink, or exists and is not a directory, is refused with `E_PREREQ_MISSING` (exit 3), because `chmod -R` and `rm -rf` would otherwise act on the link target. This includes `.cache`, `.local`, `.local/share` and the manager directories themselves. Every existing component, ancestors included, must also be owned by the current user and not writable by group or others (see the owner and mode paragraph below), because another user who can write to an ancestor could rename the manager directory under it and plant a link after the check. `install` checks HOME with the binding checks (see below) and `uninstall` checks HOME itself for the same owner and mode rule (tested with modes 0775 and 0757, nothing removed). During `install`, `versions/<semver>-<commit>` is checked the same way before and after `mkdir -p`. The name comes from the built binary, so this check runs after the build and before the binary is staged. A failure of this check is exit 1, because the build homes were already reset. The cleanup of the build directories still runs. `uninstall` checks `versions` itself and removes the version directories below it with `rm -rf`, which does not follow links. The binary is copied to a file that `mktemp` creates exclusively in that directory and is renamed into place, so a planted `dotfiles-manager.new` (file or link) is never opened. The check runs again right before the removal of `cargo-home`, `rustup-home` and `build-home` after the controls. After the swap, the cleanup checks the build directory and each build home on its own, right before it removes that tree. A tree whose check fails stays, the others are removed, and the script exits 1 (not 3): the new version is already current, and the message says so and names the trees it left. The gap between check and use is seconds. `~/.local/bin` gets the same check (a real directory owned by the current user and not writable by group or others) before the command link is staged and before `uninstall` removes the command link, and the command path is tested again immediately before the rename and read back inside the same step. A same-user process can still replace a component between a check and its use; that is the accepted same-user risk below.

The toolchain tree digest records only the owner-execute bit of each file, so both checkers refuse a toolchain tree with any group- or world-writable file or directory (tested, including the fixture differential test). Both checkers also require `toolchains/<pin>` and every entry inside it (a symlink counts as an entry) to be owned by the current user, else `E_TOOLCHAIN_MISMATCH` (exit 3), because another owner could rewrite an entry after the digest. Root is not trusted. The digest checks also fail closed when `find` itself fails (tested with an owner name `find` cannot resolve). The ancestors of `toolchains/<pin>` (`.local`, `.local/share`, the manager directory and `toolchains`) must each be a real directory (a symlink is refused), owned by the current user and not writable by group or others. The script's `install` enforces this in `check_data_tree` (`E_PREREQ_MISSING`). `self-check --build-controls` enforces it before the digest with `E_TOOLCHAIN_MISMATCH`, since the Rust side has no prerequisite code (tested with group-writable and linked ancestors, `a_linked_or_open_toolchain_ancestor_is_refused_by_the_manager`). A missing ancestor is not an error there; an absent toolchain is refused on its own. If `id -u` fails, `self-check --build-controls` exits 1 with `E_IO_FAILED` instead of blaming the toolchain (not tested, because a test cannot make `id` fail). The owner rule is tested only with an injected user id (`DFM_TEST_UID` for the script, a `uid` argument in unit tests for the Rust checker, which cover `toolchain_tree_digest_as` and the ancestor check), because a test cannot create a file owned by another user.

Owner and mode of the manager directories. The same hierarchy checks also require each existing component of those paths, that is `~/.cache`, `~/.local`, `~/.local/share`, `~/.local/bin` and each of `~/.local/share/dotfiles-manager`, `toolchains`, `versions`, `versions/<name>` (install only, after the build), `cargo-home`, `rustup-home`, `build-home`, `~/.cache/dotfiles-manager` and its `build` directory, when it exists, to be owned by the current user and not writable by group or others (`E_PREREQ_MISSING`, exit 3, before any change, for `install` and `uninstall`; tested with modes 0775 and 0757 on each, `~/.cache`, `~/.local`, `~/.local/share` and `~/.local/bin` included, except `versions/<name>`, which only `install` checks and which has a test with mode 0775 that uses a stand-in `cargo`). The owner branch is tested only with an injected user id (`DFM_TEST_UID`), because a test cannot create a directory owned by another user.

## Not verified

Device behavior on the personal M5 and work M3 (DG-1, C09): Cargo configuration discovery with the pinned Cargo, whether the empty build environment suffices on each device's Command Line Tools, ad-hoc signing under device policy, and the real toolchain digest. The install test used a minimal copy of the authoring machine's toolchain, not an official release distribution install. The missing-tools refusal was exercised only with the test hook, not on a machine that lacks the tools (device gate). The clone path was tested with a `file://` origin only; no test clones the canonical `https://` origin, and no live install has run without `--source` yet (the M5 installs used a local checkout). The lock holds `toolchain` and `toolchain_tree_sha256` only; no channel manifest digest is carried or checked (toolchain install is a later typed operation).

The differential test cannot place two paths that differ only in case on this file system, so the case-collision rule is covered by a unit test in `dfm-model` and by manual reasoning for the awk version only.
