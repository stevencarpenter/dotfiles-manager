# Durable state

This page records what the state store does where [docs/architecture.md](architecture.md) (the contract) leaves a choice open. The contract wins where this page is silent.

## What exists

| Part | Location |
| --- | --- |
| Pure document types, strict parsing, redaction, time formatting | `crates/model/src/state.rs` |
| Source lock and origin grant documents | `crates/model/src/lock.rs` |
| Storage validation, writer lock, atomic writes, journal, ledger, receipts, trials, grants, snapshots, reconciliation | `crates/engine/` (`dfm-engine`, depends on `dfm-model` only) |
| `bind` initializes state. `state check`, `state recover`, `state resolve` | `crates/cli/src/lib.rs`, `crates/cli/src/state_cmd.rs` |
| Recording commands for tests (`__record-op`, `__record-trial`, `__reconcile`) | `crates/cli/src/state_cmd/harness.rs`, compiled only with `test-isolation` |
| Failure injection (error, abort, wait for a file, request a stop, and the nth hit of a point) | `crates/engine/src/fail.rs`, behind the engine feature `failpoints`, which only `dfm-cli/test-isolation` enables. A gate test rejects it in a release dependency graph. |

`platform_macos` holds HOME, paths and the platform check. The engine does not depend on it: it takes the one OS fact it needs (the user id) from the caller in `Sys`. File operations go through `rustix` (see Decisions). The only direct `libc` use is the signal handler (`crates/engine/src/signal.rs`).

The writers are `bind`, `apply` and its scoped forms (`secrets`, `packages`, `services`), `sync` (origin grants, then one apply), `trial` (a trial record, [docs/trial.md](trial.md)), `state recover` and `state resolve`. Trial `adopt` and `purge` are not built.

## Layout

```
~/.config/dotfiles-manager/machine.toml            binding
~/.local/state/dotfiles-manager.lock               writer lock (flock), outside the state root
~/.local/state/dotfiles-manager/state/             0700
    state.json   ledger.json   journal.jsonl       0600
    salt                                           0600, 32 bytes, created by Store::init
    grants.json                                    0600, origin grants (sync --trust-origin)
    receipts/ snapshots/ trials/                   0700
~/.local/state/dotfiles-manager/state.next/        only during init
```

The architecture table lists `state/ledger.json` relative to the state root `~/.local/state/dotfiles-manager/`. This implementation reads that literally: the files sit in a `state/` directory inside the root. That is also the only reading under which `state.prev-<n>` and `state.next` are siblings of `state` and the lock "in the parent directory" is outside it. `state check` accepts `grants.json` and `salt` as known entries and reports any other file in `state/` as a stray.

The binding has schema 2, which records the checkout root (DFM-61). A schema 1 binding (no root) stays readable; every command then needs `--root` until `bind` upgrades it (rule 7).

## Documents

All are JSON in canonical form (UTF-8, sorted keys, no extra whitespace), at most 16 MiB (journal lines 64 KiB), nesting depth at most 32, unknown keys refused. The size cap is checked first, so an oversize document is never parsed. The schema is read right after the JSON parse and before the nesting check: `2` is accepted, a higher integer (also one above `i64`) is `E_STATE_NEWER`, any other integer is `E_SCHEMA_UNSUPPORTED`, a missing or non-integer one is `E_STATE_INVALID`. A document nested past the JSON parser's own limit of 128 fails to parse. A scan that does not recurse then reads its top-level `schema` (an unsigned integer), so a newer document is still `E_STATE_NEWER`; any other such document is `E_STATE_INVALID` as invalid JSON. The ledger, receipt, trial and journal validators also check `schema` on write.

- `state.json`, `ledger.json` and each trial carry `binding{profile, machine_id, binding_digest}`. The receipt carries `profile{id, binding_digest}` and `machine_id` as the contract lists them.
- **Identity is profile plus machine id.** `binding_digest` is audit evidence and is never compared, because an authored binding edit changes it without changing the owner.
- Every document written for another identity than `state.json` is refused on write (ledger, receipt, trial) and reported on read.
- **Link count.** Every state document read through `read_private` (journal, ledger, state, receipts, snapshots, trials, salt) and the manager lock file must have exactly one hard link. A second name is `E_STORAGE_INVALID`: `state check` reports it as a finding (exit 1) and the lock is refused before any byte of the lock file is changed, so the shared inode is never truncated or written.
- **Salt.** `state/salt` is 32 random bytes from `/dev/urandom`, mode 0600. `Store::init` creates it with the rest of the state, so a plan can salt a content token before any merge. Later it is created only by `Store::salt_or_create` under the writer lock, published with an exclusive rename (`RENAME_EXCL`), so a racing writer cannot replace it. A reader (`plan`, `doctor`) uses `Store::salt`, which never creates it. A file that is a link, is not exactly 32 bytes, or has a wrong owner or mode is `E_STORAGE_INVALID` with the move-aside text and is never replaced. `bind` on a store with such a salt fails the same way (exit 3), writes nothing and does not report `already bound`.

  A store made by an older build has no salt. `bind` run again with the same profile and machine id creates it and changes nothing else, but only when the ledger records no salted hash. With a recorded hash `bind` fails with `E_STATE_INVALID` and the restore text, because a new salt would not match it. A ledger that cannot be read proves nothing: `bind` fails with the ledger's own code (exit 3), writes nothing and creates no salt. The first merge creates a missing salt. `state check` validates the salt (a regular file, owned by the user, mode 0600, exactly 32 bytes, not a link) and reports any other state as `E_STORAGE_INVALID`. A missing salt while the ledger holds a `coowned` record is reported as `E_STATE_INVALID`.
- **Lost salt (hard state error).** A salt that is missing or unusable while the ledger records a salted hash cannot be rebuilt: the stored hash is useless without it. Plan and apply refuse with the recovery text and write nothing. For an unusable salt (wrong mode, size or a link) the text says to move the file out of `state/`, and it says the ledger records a salted hash only when it does. When the ledger cannot be read, the text says the answer is unknown, gives the ledger error and does not advise a new salt, and `state check` reports a missing salt beside it. A `retire` needs no salt ([docs/apply.md](apply.md), "Merge") and still runs. No command repairs it, and `state resolve-salt` is not built. The operator restores `state/salt` from a copy, or edits `state/ledger.json` by hand and deletes the `coowned` object (the key under `resources[].owned_outputs[]`) of each co-owned output. The next apply then treats the file as one with no ledger entry and needs `--allow-adopt` for it. The salt never appears in any other file or output. A state upgrade must copy it unchanged into `state.next/` (architecture section 8 item 7).
- **Ledger entries.** One entry per resource with its exact `owned_outputs`. Two resources cannot own one path, and one resource cannot list one path twice. Paths that differ only by case name one output on APFS, so uniqueness is checked on the case-folded path (the fold the planner indexes by). A ledger with both `.config/foo` and `.config/Foo` is `E_STATE_INVALID`, and the extra entry must be removed by editing `state/ledger.json` by hand. The helpers that update the ledger (record, drop, co-owned record, recovery) match an entry by the folded path, so an output re-cased by a plan replaces the old spelling in place and never adds a second entry. `authorizes_delete` still compares the exact text.
- **Ledger paths.** Paths are normalized absolute paths inside HOME, checked on read as well as on write. They may not be inside, equal to, or an ancestor of the state root, the config directory, the lock file, the data directory (toolchains) or the cache directory (build). Comparison is case-folded text and also by filesystem identity (device and inode, symlinks followed above the leaf): a directory above the claim that is a reserved directory, or a leaf that is a reserved path or an ancestor of one, is refused, so a case or Unicode alias (APFS folds `U+017F` to `s`) or a link into the manager's storage cannot pass. A symlink as the leaf is allowed, because the link itself is the claim. The ancestor rule applies to claims only. A directory the manager creates while it is missing (a `create-dir` operation and its journal entry) may be an ancestor of a reserved path, because a missing directory holds nothing reserved. It may not be a reserved path or lie inside one. A parent that resolves outside HOME through a link is `E_PARENT_UNSAFE`, not `E_STATE_INVALID`. The same check runs on every path read from the ledger, receipts, trials and journal, and again in `authorizes_delete` at the moment of use. On write, symlinks in the parent directories are resolved first. A hand-written ledger that violates this is a finding and grants nothing.
- **Fingerprints.** A normal resource has a SHA-256 fingerprint: `dfm_model::plan::file_fingerprint` for a file (SHA-256 of `file\0` and the content) and `dfm_model::plan::link_fingerprint` for a symlink (SHA-256 of `link\0` and the target text). The prefixes keep the two apart, so a file whose bytes spell a link fingerprint never matches. A sensitive resource has no fingerprint. `authorizes_delete` needs a normal entry for that resource and path whose fingerprint equals the live one. A mismatch, a missing entry or a sensitive resource authorizes nothing.
- **Co-owned record.** A co-owned sensitive output carries `coowned{managed_hash, entries[{id, key, sha256}], appended[{pointer, sha256}], leaves}` instead of a fingerprint: the salted hash of the managed fields the manager last wrote, the handler entries it added, and the array items it appended under an `append` key. `pointer` is the JSON pointer of the array in the settings file and `sha256` is the hash of the item the module declared, not of live content. The salted hash covers the merged managed view, fragments included, without the `append` arrays. `leaves` maps the JSON pointer of each managed leaf to its salted hash, so the conflict check compares leaf by leaf and a dropped key is no edit. `appended` and `leaves` are left out when empty, and a ledger without them reads as before. The validator accepts `coowned` only for a sensitive resource, requires a well-formed hash, and accepts only canonical pointers outside `hooks` for `appended` and `leaves`. A `(key, sha256)` pair may appear once in `entries` and a `(pointer, sha256)` pair once in `appended`, else the ledger is `E_STATE_INVALID`, because a retire removes one live element for each record. An earlier build could write such a repeat (a `takeover` merge of two handlers with identical content recorded the pair twice). The repeat must be removed by editing `state/ledger.json` by hand. A secret output (`op-template/v1`, [docs/secrets.md](secrets.md)) uses the same record: `managed_hash` is the salted hash of the rendered bytes, with empty `entries`, `appended` and `leaves`.
- **Receipt.** The contract fields. `result.outcome` is the exit name and must match `exit_code`: `ok` 0, `failed` 1, `usage` 2, `blocked` 3, `declined` 4, `pending` 5, `interrupted` 130, `terminated` 143 (see Decisions). An operation has `started_at` and `finished_at` unless its status is `not_started` or `not_in_scope`, where both are absent. `counts` has one key per status and must equal the tally of `operations`. A sensitive operation carries no `before` or `after`. `error` and `command` are bounded to 4 KiB. Exit 0 cannot hold a `failed`, `unknown`, `blocked`, `blocked_pending` or `pending` operation. Exit 1 with none of them is valid: a run can stop after a mutation (for example when settling an earlier journal fails) while every operation is `current` or `not_started`.
  - `approvals[{operation_id, how, at}]`: one per disruptive operation or adoption that ran. `how` is `allow_disruptive` or `allow_adopt`; any other value (`interactive` included) is refused. The validator checks that `how` fits the operation's shape: `allow_disruptive` needs an operation that owns nothing and has no `after`, and when it is `updated`, a `before` (a removal) or `reload = reloaded` (a service restart). `allow_adopt` on a normal operation needs no `before` and no `reload`, and when it is `updated`, an `after` and an owned output. `allow_adopt` on a sensitive operation (a merge takeover) needs no `before`, and when it is `updated`, an owned output. A failed or blocked operation has neither shape, so only `how` is checked for it.
  - `operations[].reload`: one of `not_attempted` (a published file or link), `requested` or `reloaded` (a service operation, [docs/lifecycle.md](lifecycle.md)).
  - A path source is `{id, tree}` with no commit.
- **Journal.** `intent` (with `recovery{outputs[{path, existed_before, expected_sha256?}], snapshot?}`; `expected_sha256` holds the `file_fingerprint` of the planned content, not a plain SHA-256), then one of `done`, `failed`, `blocked`, `pending`, `unknown`. An `intent` without a later outcome for the same `(op_id, op)` is an interruption record. `token` is bounded to 4 KiB and `snapshot` must be a valid id.
- **Trial.** `trial_id`, `tool`, `baseline{tool_preexisting, paths[{path, existed, sha256?}]}`, `owned_outputs`.
- **Times.** Every time stamp (`at`, `started_at`, `finished_at`) is UTC with nine fraction digits, `2026-10-10T12:00:00.123456789Z`. A stamp in another form, including the whole-second form, is refused. A receipt is named `<compact start>-<op_id>.json`, for example `20261010T120000.123456789Z-run-1.json`. `created_unix_ns` in `state.json` and in a trial, the generated op ids (`run-<ns>-<pid>`, `journal-repair-<ns>`, `binding-upgrade-<ns>`) and the lock note use nanoseconds since the epoch. The macOS clock has a resolution of one microsecond, so the last three digits are zero there. This form is state schema 2. Schema 1 (whole-second stamps, `created_unix`) was written only by pre-release builds, and no reader or upgrade exists for it: every schema 1 document is `E_SCHEMA_UNSUPPORTED`, and the recovery is to move the state directory aside and bind again.

## Rules that the code enforces

1. **Topology (C08).** HOME is resolved once through every alias (`/var` to `/private/var`, a link above HOME) and opened. The CLI builds every path from that resolved spelling (plan targets, ledger, recovery), so a password-database HOME that contains an alias does not put paths outside the store's scope. Everything below it is reached with `openat` relative to a descriptor, with `O_NOFOLLOW` (`O_DIRECTORY` for directories), and checked on the opened descriptor (`fstat`), never by path. Every component of the config directory, the lock directory and the state root must be a real directory (never a symlink, never another file type) owned by the current user. State root and below must be exactly 0700. Existing shared parents and the config directory must not be group or world writable. Files must be regular, owned by the current user and 0600. A violation is `E_STORAGE_INVALID` (exit 3). Nothing is repaired or replaced.
2. **Writer lock (C01, C05).** Mutating paths take an exclusive `flock` on the lock file without waiting. A second holder gets `E_LOCKED` (exit 3). The kernel releases the lock when the process ends, so an abrupt exit cannot leave it held. The lock file opens relative to a held directory descriptor, non-blocking, and must be a regular file owned by the user with mode 0600 (a mode the umask tightened is set to 0600). The holder compares the locked file with the entry in the held directory before every write. If the file was removed or replaced, the holder refuses to write (`E_LOCKED`). A second command can still lock the new file, so removing the lock file lets a second writer start, but the first writer is fenced and writes nothing more.

   Read-only commands take no lock, except `state check`. It takes a non-blocking shared try-lock on the existing file (never creating it, never following a link), holds it until it ends, and returns `E_LOCKED` with no findings when a writer holds it. A lock file the writer would refuse (another owner, more than one hard link, a mode looser than 0600) is `E_STORAGE_INVALID` here too, so `state ok` never hides a blocked writer. After the lock it compares the opened file with the entry now at the lock path (device and inode, no follow), as the writer does, and again after the read. A replaced or removed lock file, or a mismatch, gives `E_LOCKED` with no findings, because a lock on it excludes no writer. When no lock file existed at the start, it holds no lock. A lock file that exists after the read (a first `bind` ran during it) gives `E_LOCKED` with no findings too.
3. **Atomic persistence (C01, C05).** Replacement is a same-directory 0600 temporary file, `fsync`, `rename`, directory `fsync`. A failure before the rename leaves the previous file. A failure after it is `E_IO_UNCONFIRMED` (exit 1): the new file is in place and only its durability is unknown. New directories and the journal are `fsync`ed, with their parents. Receipts, snapshots and new trial records use create-only publication (an exclusive rename, `RENAME_EXCL`) and are never overwritten. The journal is append-only with `fsync` and refuses to extend a file whose last line is torn. A failure of the append `write` itself, after the append began, is also `E_IO_UNCONFIRMED` and counts as a mutation: part of the line may be in the file, so the journal may now end in a torn line. A failure of the `fsync` after a complete write is `E_IO_UNCONFIRMED` too. The next `apply` or `state recover` repairs a single torn final line: it cuts the bytes after the last newline, then journals a `failed` entry (`op` `repair`, reason "torn line repaired: removed N bytes") before any other write. A torn or damaged line that is not the last one is not repaired: the journal stays unreadable and every command refuses it. `state check` only reports.
4. **Intent before effect (C02).** The order is: intent with recovery metadata (`fsync`), effect, independent read-back, outcome entry, ledger update, receipt. Ownership of a new output is recorded only after the outcome entry ([docs/apply.md](apply.md), "Order", step 9, has the one exception for an owned output).
5. **Reconciliation (C02, C03, C05).** `reconcile` asks a probe (the operation's `already_done` check) and journals `done`, `failed` or `unknown`. It never runs the operation again and never creates ownership. The one ledger edit is for a finished `update_file` or `replace_link`: an entry that already owns the path with the old fingerprint moves to the fingerprint that is live, before `done` is journaled.

   **An output whose ledger write was interrupted stays unowned, and no run records it by itself.** Until it is adopted, it is never removed. This is the safe direction. Adoption is the path that records it: the planner emits an `adopt` operation for an unowned link whose target text equals exactly the planned link, and apply records the ledger entry when the owner passes `--allow-adopt <operation-id>` and the link still matches ([docs/apply.md](apply.md), "Adoption"). It is also the migration path for an existing stow or chezmoi setup. A regular file whose ledger write was interrupted is not recovered this way.

   **An `unknown` outcome blocks its path across runs.** An `unknown` result (by `reconcile` or by an unconfirmed durability result) is not terminal. The path, its ancestors and its descendants stay blocked in every run, compared case-folded, until the entry is settled. Every `apply` and `state recover` probes each open `unknown` entry again with the operation's `already_done` check, through the opened HOME, before any operation runs. An entry that `reconcile` wrote in the same call is not probed a second time.

   - The probe says done: the journal gets `done` ("recovered: done"). A removal drops the ledger entry of the absent path.
   - The probe says done for a created, replaced or adopted link or file: ownership is recorded only when every rule below holds. Otherwise the entry is closed without ownership, and the next plan offers `adopt` for an exact link.
     1. The `unknown` entry carries the mark `unconfirmed:` in its reason. The executor writes it when it had seen the effect and only durability was unconfirmed. An entry written by `reconcile` (the effect could not be observed) has no mark: a match that appears later was not seen to match then.
     2. The live fingerprint equals the `expected_sha256` of the intent.
     3. A create operation did not find the path present before (`existed_before` is false).
     4. The leaf is owned by the current user, and a link resolves to a regular file.
     5. The resource is known. In `apply`, the resource has a ledger entry or the current plan has an operation for that resource and path. In `state recover` there is no plan, so the resource must already have a ledger entry. A new resource is settled `done` without ownership there, and the next plan offers `adopt`. The ledger lookup for this rule runs before the `done` entry is written. A ledger that cannot be read fails the run with the ledger's code and leaves the entry open (`unknown`), so the next recover after the repair settles it and updates the ledger.

     The recorded mode is the live mode of a file (the intent carries no mode) and 0777 for a link. The recorded fingerprint is the intent's `expected_sha256` (`Own::Auto`), not a fresh observation. A file that changes after the probe read it and before the ledger write is recorded as owned with that stale fingerprint, and the next plan refuses it as drift.
   - The probe says not done (the path is gone, or a removal target is still there unchanged): the journal gets `failed` ("recovered: not done"). The path is free.
   - The probe cannot decide, the entry has the `unconfirmed:` mark, and the live entry is a readable file or link with another fingerprint: the journal gets `failed` ("recovered: not done; a later match is not owned"). The executor saw the effect when it wrote the entry, so a different file is not that effect, and a match restored by hand later is never owned automatically. The next plan offers `adopt` for an exact link, with its approval. A directory, an unreadable entry or a path outside HOME does not close the entry.
   - The probe cannot decide: the entry stays as it is, and every operation on that path is `blocked` with `E_OP_INTERRUPTED`. The text names the journal id and the fix.
   - An intent with more than one path is not probed (the manager writes one path per intent, and probing only the first would settle the others unseen): it stays `unknown`, blocks all its paths, and only `state resolve <journal-id> --as failed` clears it.
   - An `unknown` entry with no `intent` entry, or whose intent lists no path, has nothing to probe. It blocks every operation of its resource (`E_OP_INTERRUPTED`, naming the journal id). Only `state resolve <journal-id> --as failed` clears it.

   `dfm state recover` runs this settling alone: it needs no plan and no allowance flag. It takes the writer lock, journals what it settles, writes no receipt, prints each entry it settled and each that stays open, and exits 0 when nothing stays open. It exits 3 with `E_OP_INTERRUPTED` naming the open journal ids otherwise. After an unconfirmed `replace_link`, the link shows the new target while the ledger still holds the old fingerprint. A plan calls such a link `current`, so only recovery fixes the ledger entry. `state recover` does that without an approval flag. `apply` does it too. When apply settles a link that the same plan re-plans as `adopt`, the adoption still needs its `--allow-adopt` flag to pass the gates, then ends `current`.

   `dfm state resolve <journal-id> --as done|failed` settles one entry by hand. It takes the writer lock and appends one entry with the reason "resolved by operator". `--as done` runs the same probe and needs the answer done, and then records ownership under rules 2 to 4 (the operator replaces rules 1 and 5). A mismatch exits 3 with `E_CONFLICT` and writes nothing. `--as failed` needs no check. A resolution writes no receipt: the journal entry is the record. An id that names no open `unknown` entry is a usage error (exit 2). Entries pair by `(op_id, op)`. The recovery metadata comes from the intent entry, because the `unknown` entry carries none.

   The planner does not read the journal. A plan with a blocker cannot be approved, and a plan blocked on an open `unknown` could never be applied, so the apply that would settle it would never run. The block therefore happens in `apply` at settle time. `doctor` and `status` read the journal and show each open entry as `ERROR E_OP_INTERRUPTED`, and `state check` reports it as a finding. A plan can show a path as plannable while an open entry still blocks it. Apply then blocks the operation. When settling changes the ledger, an `adopt` operation planned before it finds that exact link recorded for its resource and ends `current`. Any other change makes it `E_PLAN_STALE`. Another operation planned before settling can end `blocked` with `E_PLAN_STALE`. The next plan reflects the settled state.
6. **Init (C01).** `state.next/` is built and renamed to `state/`. A crash leaves no `state/` or a complete one. An existing `state/` that is not an empty directory is never recreated: lost or damaged state needs inspect-and-adopt. The engine's `init` accepts an empty `state/` and replaces it, and only the open for `bind` allows it. `bind` itself reads the store first and refuses an empty `state/` as state loss (`E_STATE_INVALID`) before any write, so the CLI never reaches that case. A writer also refuses a `state/` that lacks `receipts/`, `snapshots/` or `trials/` with `E_STORAGE_INVALID` before any change; a reader opens it and `state check` reports the missing directory.
7. **Bind order (C07, C11).** Before phase 1, `bind` refuses a profile whose top-level `platform` or `architecture` differs from this machine with `E_PLATFORM_MISMATCH` (exit 3) and writes nothing, because rebinding is unsupported and every later `plan`, `doctor` and `apply` would refuse it. A missing key is left to the resolver. Phase 1 is read-only and refuses a different identity (in the binding or in `state.json`) with `E_REBIND_UNSUPPORTED` before any write, including the lock file. Phase 2 takes the lock, decides again, writes `state/` first and the binding second. A crash between them can only be completed by the same identity. There is no force flag and no command infers a profile.

   A binding with no state directory is state loss: `bind` refuses with `E_STATE_INVALID` (exit 3) and writes nothing, `state check` reports it as a finding (exit 1), and writers refuse without creating the state root. Only a bind that finds no binding may create state. A binding written before the state store existed has no state: move it aside and bind again, or restore the state directory.

   A bind with the same identity on a schema 1 binding (no root) needs the existing state. Under the lock it replaces the binding atomically with the schema 2 form between an `upgrade` intent (op id `binding-upgrade-<ns>`, resource `binding`, no recovery outputs) and its `done` entry, or `failed` when the write stopped before the rename. A run that dies in between leaves the intent open, which `doctor` and `state recover` report. A recorded root is never changed: `bind --root` with another directory is refused.
8. **State check (C06).** `dfm state check` is read-only. Topology and directory-level refusals are findings with exit 1, like a diagnostic command, not an abort. It loads every document and reports each problem by file: `E_IDENTITY_MISMATCH` for a readable document written for another identity, the document's own code for an unreadable one (it hides nothing else), `E_OP_INTERRUPTED` for an intent without an outcome and for an `unknown` entry that no later entry settled. Listing errors and unreadable directories are reported too. Every snapshot directory name must be a valid operation id, even when the directory is empty. Every snapshot payload must be a validly named private file (owned by the user, mode 0600, a regular file, no symlink); a symlink, directory, wrong mode or bad name is a finding. Every trial baseline and owned-output path passes the same claim check as a receipt path, so a path under a link parent is a finding. A stray entry (`state.next`, a temporary receipt, trial or snapshot, an unexpected file in the state directory, a staging or previous state directory next to it) is an `E_STATE_INVALID` finding that counts toward the exit code. Exit 1 with `E_DIAGNOSED` when there are findings, 0 otherwise. While a writer holds the lock the open intents and temporary files it leaves are normal, so `state check` prints that a writer is running and exits 3 with `E_LOCKED`; run it again after the writer ends.
9. **Exit after a mutation.** A refusal that happens after a mutation began exits 1, not 3 (section 10). `Refusal::after_mutation` marks it. `bind` marks refusals after it created the state directory, and the harness marks everything after the intent entry.
10. **Held descriptors and re-check (S1, C08).** A `Store` holds open descriptors for the state root and for `state/` for its whole life, and every read and write is relative to them. A path component swapped for a symlink or another directory after the store was opened cannot redirect a write: the descriptor still names the directory that was verified. Before each ledger, journal, receipt, trial, grants or snapshot write the store also checks that the lock is still the locked file, that the held root and `state/` are still the entries their paths name (a swap is refused, `E_STORAGE_INVALID`, and nothing more is written), and that their owner and mode are unchanged. Subdirectories are opened without following a link at the moment of each write. Test: `state/` is swapped for a link to a foreign directory while a ledger or journal write is parked at a failpoint. The write completes inside the original directory, the foreign directory stays empty, and the next write is refused.
11. **Redaction.** One pass over every persisted free-text field (receipt command and operation error; journal reason and token). Fields with a fixed shape are validated instead (rule 13). Overlapping matches merge, including a match that overlaps itself. Control, bidirectional and zero-width characters become visible escapes. Each such text is bounded to 4 KiB (the validators refuse a stored `command`, `token` or `reason` above it). A resource, adapter, id or path that contains a known secret is refused, not redacted, because redaction would break its use. The refusal text does not repeat the value. Release builds never call `Store::with_secrets` (only the isolated test harness does), so the known-secret list is empty there and redaction removes nothing. Escaping and bounding still run. `write_snapshot` and `write_trial` have no release caller (`trial` uses `create_trial`). Both stay public because the engine tests build without the `failpoints` feature.
12. **Durability.** File and directory syncs use `File::sync_all`, which asks for `F_FULLFSYNC` on macOS. A directory that rejects that request gets a plain `fsync` instead. Whether data reaches the medium cannot be observed by any test here, and tests that abort the process leave the page cache intact, so they show recovery from a crash of the manager and say nothing about power loss.
13. **Write caps.** A ledger, receipt, trial or snapshot over 4 MiB is refused before anything is written, and an append that would take the journal past 8 MiB is refused. The read cap stays 16 MiB, so a document the manager wrote is always readable. Rotation is not built, so a journal at its cap refuses every append, which stops every operation that must journal its intent first. The apply gate also counts the entries that settling earlier work appends, so a journal near the cap refuses before any write. Reads and `state check` still work. The refusal text points to the hand procedure in "Recovery by hand". Receipt fields that carry no free text (outcome, hashes, source identities, approval, operation times and names) must have their exact shape.
14. **Mutation tracking.** A `Store` records its first write that took effect (or whose result is unconfirmed) and stamps every later refusal as after a mutation, so the exit is 1 whatever the caller does. Recovery also counts successful staged-copy removals, so a later refusal (including a full journal) exits 1. Missing staged copies and failed removals do not count as mutations.

## Decisions and ambiguities resolved

| Contract text | Reading used |
| --- | --- |
| Section 4: `state/ledger.json` under "State root: `~/.local/state/dotfiles-manager/`" | Files live in `<root>/state/`. See Layout. |
| Section 5 receipt: `result{outcome, ...}` | `outcome` is the exit name of `exit_code` (the section 10 table). Operation times are optional only for `not_started` and `not_in_scope`, and those two statuses must carry neither `started_at` nor `finished_at`; every other status needs both. |
| Section 5 receipt: `profile{id, ...}` and `class` per operation | `profile.id` is the canonical profile path, the binding's identity. `class` is the sensitivity class (`normal` or `sensitive`), because the receipt rule for sensitive operations keys on it. |
| Receipt `result.exit_code` 1 | A receipt with exit 1 is valid without a failed, unknown, blocked or pending operation. An apply that stops after a mutation (for example when settling an earlier journal fails, `execute` in `apply.rs`) ends with every operation `current` or `not_started`, and refusing that receipt would lose the record of the mutation. Exit 0 with such an operation is refused. |
| Section 10: a second mutating command gets exit 3 `E_LOCKED` | `bind` follows it. The concurrent-bind test accepts `E_LOCKED` as a loser's outcome. At least one bind still wins. |
| Section 8, "Filesystem writes": descriptor-relative `openat`/`renameat`/`fstatat` | Met for the manager's own storage, with `rustix` (below). Residual limits are listed under Known limits. |
| Section 14 decision 3 accepts `serde_json` | Pinned `=1.0.149`. Direct dependency of `dfm-model` and of `dfm-cli` (the `mise/v1` probe reads `mise ls --json`, [docs/packages.md](packages.md)). |
| Section 14 decision 3 lists four direct crates | `rustix` is a fifth, added by owner-delegated decision for descriptor-relative operations: pinned `=1.1.5`, default features off, only `std` and `fs`, safe API only, used by `dfm-engine` only. `libc` (`=0.2.190`, no default features, already in the lock file as a `rustix` dependency) is a direct dependency of `dfm-engine` for the signal handler only. A gate test checks every member's direct dependencies against an allow-list built from `cargo metadata`, that `rustix` resolves with exactly the features `alloc`, `fs` and `std`, and that one `libc` version resolves. |

## Known limits

- **Torn-line repair.** The repair cuts any final line without a newline, also a complete line that only lacks the newline; this is by design, and the cut entry's operation is settled by the probe. A journal that is a symlink is refused (not repaired) like any other journal access. Before the cut, the repair writes the cut text to `state/journal.torn`. If the repair record cannot be written after the cut, the run exits 1 and the error names that file and the start of the text, and `state check` reports the file as a stray entry until it is removed by hand. After a successful repair the file is removed; if that removal fails, the repair still succeeds and `state check` reports the file. If the cut fails or the process stops after the file is written, the journal is unchanged and the next repair finds the same text in the file and resumes the cut. A `journal.torn` that holds other text stops the next repair before it cuts, and that refusal writes nothing, so it exits 3.
- **`DFM_BINDING`** (isolated builds only) is not canonicalized like HOME. Its parent is opened relative to the resolved HOME, so a binding path with an alias spelling can be refused.
- **Snapshot check cost.** `state check` reads each snapshot payload fully (up to the 16 MiB read cap) to run the private-file checks. A store with many large snapshots makes the check slow and memory-heavy.
- **Rename of the state parent.** The writer lock holds descriptors only. A rename of `~/.local/state` (or of `~/.local/state/dotfiles-manager`) after the lock is taken is not detected by the lock.
- **Residual after descriptor-relative writes (C08).** The redirection class is closed for the manager's storage: a swapped path cannot send a write elsewhere. These remain:
  1. HOME is resolved with `canonicalize` and then opened. A swap of a system-owned ancestor of HOME between those two calls is not covered.
  2. A held descriptor does not stop another process of the same user from changing, unlinking or chmod-ing files inside the verified directory. It stops redirection only. The re-check refuses a writer after a swap or a mode change, but a change made after the check and before the write is not detected.
  3. Claims point at files in HOME that applications and adapters own. The engine resolves a claim's parent directories by path when it accepts the claim. The effect on the claimed file is the adapter's, and it must use its own descriptor-relative operations.
  4. Removing the lock file lets a second command lock the new file. The first writer is fenced (it refuses further writes) but a second writer can start.
  5. Path scope compares case-folded text, not normalized Unicode.
- **Exclusive rename.** Every create-only publication (salt, receipts, snapshots, trial records, `bind`, a created or merged file) uses `renameat` with `RENAME_EXCL`. A file system that does not support it (`ENOTSUP` or `EINVAL`) makes the create fail with `E_IO_FAILED`, and the text names the path and the missing support. There is no fallback to a link and unlink pair, because that pair leaves a second name after a crash. APFS supports the flag.
- **State upgrade (C03).** Not built. Every kind has "Upgrades from: none yet", so there is nothing to convert, and the `state.next` / `state.prev-<n>` upgrade procedure, `state upgrade`, `verify --mark`, `retire-previous` and `state/UPGRADE` do not exist. A newer or unsupported state is refused with its code and nothing is rewritten.
- **Conflict detection for sensitive paths (C04).** Built for the `claude-settings/v1` merge ([docs/adapters.md](adapters.md), "Conflict detection") and the `op-template/v1` secret output. The ledger stores the salted hash in `coowned.managed_hash` and no content fingerprint. `authorizes_delete` refuses every sensitive resource, so a co-owned file is never deleted. The contract also asks for file identity in the ledger and an interactive confirmation to overwrite. The identity is checked at the rename instead of recorded, and the confirmation is `--allow-adopt`. No other sensitive producer exists.
- **Trial baseline class (S6).** A trial baseline has no sensitivity class. A baseline path hash is stored for any path. It is the file fingerprint, the same value an observation records.
- **Bind orchestration (R8).** `bind` sequencing lives in the CLI crate, not the engine.
- **Strict-parser gaps (R12).** Known gaps remain in how strictly the parsers reject unusual but valid JSON (for example duplicate keys, which `serde_json` accepts, last one wins).
- **Application-owned data.** The engine accepts only exact paths inside HOME and outside its own paths. Deciding that a path inside HOME belongs to an application is the adapter's evidence.
- **Redaction** removes known secret values only. It does not detect unknown credential patterns.
- **Not built:** snapshot retention and pruning, journal rotation and the `Fs`/`Clock` ports.
- **Non-UTF-8 names.** A non-UTF-8 entry name is reported as a finding by code, but it has no test, because APFS rejects such names.
- **Lenient reads.** `read_ledger_lenient` and `read_journal_lenient` do not refuse the whole read when one stored path fails the claim check, for example a parent that became a link leaving HOME (a stow-style setup). The planner and apply use them, so one unsafe entry blocks only the operations on that entry. `read_ledger` and `read_journal` stay strict. `write_ledger` checks new or changed outputs and skips an unchanged old one. Nothing is read, written or deleted through an unsafe path.
- **Journal scope.** `read_journal_lenient` rejects the whole journal when one entry has a path outside the claim scope. Settling and `state recover` then fail until that entry is fixed by hand.
- **Duplicate journal ids.** `state resolve` needs one open entry per journal id. Two open entries with the same id are a usage error, and neither can be resolved by id. Apply writes distinct attempt ids, so only a hand-edited journal or a harness run causes this.
- **Evidence scope.** The CLI tests drive the `test-isolation` build through `--home`, not the installed release binary. The recording commands exist only in that build.

## Recovery by hand

- `E_STATE_INVALID`, `E_STATE_NEWER`, `E_SCHEMA_UNSUPPORTED` on a document: keep the file. Use the binary version that wrote it, or restore from a copy. No command rewrites it.
- `E_REBIND_UNSUPPORTED` against existing state: the state directory belongs to another identity. Move `~/.local/state/dotfiles-manager/` aside yourself if that machine identity really is retired.
- Stray entries reported by `state check` (a temporary file from an interrupted write, `state.next`, `journal.torn`): read each one, then remove it by hand after you confirm that no apply is running. `state check` returns `E_LOCKED` with no findings while a writer holds the lock, so a running apply is never reported as damage. `state recover` does not delete strays.
- Journal at its cap (8 MiB; no compaction code exists). Do this with no manager command running:
  1. Run `dfm state check`. It must not return `E_LOCKED`.
  2. Copy `state/journal.jsonl` to a place outside the state directory. Keep the copy as the audit record.
  3. Choose what to drop. A journal id is the `op_id` without its last `-<n>`. Drop all lines of a journal id or keep all of its lines. Never drop part of one. Keep every id that has an open operation (the last line of an `(op_id, op)` pair is `intent` or `unknown`). Attempt numbers are the count of `intent` lines per journal id, so a partly dropped id would give a new attempt the same `op_id` as a surviving one, and its outcome line would settle the wrong intent. A fully dropped id restarts at `-1`.
  4. Write the kept lines in their original order to `state/journal.jsonl.new` with mode 0600. This filter keeps every id that has an open operation and drops every other id as a whole:
     `jq -sc 'def jid: sub("-[0-9]+$";""); (group_by([.op_id,.op]) | map(select(last.phase | IN("intent","unknown"))) | map(.[0].op_id | jid)) as $open | .[] | select((.op_id | jid) as $j | $open | index($j))' state/journal.jsonl > state/journal.jsonl.new`
  5. Move the new file over the old one: `mv state/journal.jsonl.new state/journal.jsonl`. Check that the mode is 0600 and the file ends with a newline.
  6. Run `dfm state check`. It must report the same open operations as before and no new finding.
- `E_OP_INTERRUPTED`: a later `apply` decides with the operation's `already_done` check. When the probe cannot decide, check the path, then run `dfm state resolve <journal-id> --as done` (the path holds the result the operation expected) or `--as failed`. `dfm state recover` settles what the machine shows clearly without a plan. The isolated test binary has `__reconcile` for the first step.
