One repository, three machines

Every Mac runs the same binary and reads the same public repository. What differs is one file per machine: the profile it is bound to. The profile selects modules; the resolver closes their requires; adapters write only what the composition claims. A work machine adds a private bundle that extends the public one, so work identity and hooks never enter the public repo. Nothing is inferred from the hostname, and no machine holds a stack of profiles.

Three ways a machine differs, and nothing else

  1. Selection. The profile lists modules. A module that is not selected, directly or through requires, writes nothing on that machine.
  2. Override. A profile or module replaces one value at a path the owner listed in policy.defaults, with a reason. The work editor, the server editor and the aerospace variant are overrides.
  3. Contribution and fragments. A module adds a key under a map the owner exposed in policy.extensions (the work session hook), or drops a file into a fragment directory an assembly reads (40-work.md into .codex/AGENTS.md).

Every effective value carries provenance: owner, original, the change, who changed it, the reason and the source file. explain <resource> prints it per machine.

Add a fourth machine

  1. Write profiles/<id>.toml: bundle, platform, architecture, modules.
  2. On that machine: install the binary, bind --profile … --machine-id <id>, then plan.
  3. Nothing else changes. The other machines' plans are unaffected because they resolve their own binding.

Invariants that make this safe: one binding per machine and no --profile flag on mutating commands (docs/architecture.md section 6); a platform or architecture mismatch refuses before any write (E_PLATFORM_MISMATCH); the public closure may not reach an external source; state, lock and receipts live per machine under ~/.local/state/dotfiles-manager/.

Configure tools in your dotfiles repository

The manager reads three kinds of TOML document from your dotfiles checkout and binds the machine to one profile. A tool's configuration is one or more resources in a module, with the files beside the manifest. Nothing here is a template language: values are data, adapters are code.

Layout of the checkout

  • base/bundle.toml one per repo: core, catalogue, [sources]
  • base/modules/core/module.toml always selected, cannot require others
  • base/modules/core/files/… sources the core links or reads
  • base/modules/m5/module.toml this machine's tools
  • base/modules/m5/files/… zshrc, nvim/, AGENTS.md fragments
  • base/modules/agents/module.toml shared tools other modules extend
  • profiles/m5-01.toml one per machine; selects modules, overrides defaults
  • external/bundle.toml optional: a private bundle that extends base

Paths in a manifest are relative to that manifest. target is relative to HOME. The bundle's [sources] roots are relative to --root, the checkout.

Get the machine on it

  1. Bind once: dotfiles-manager bind --profile <checkout>/profiles/m5-01.toml --machine-id m5-01
  2. See what a resource resolves to: dotfiles-manager explain m5.zsh --root <checkout>
  3. See what would change: dotfiles-manager plan --root <checkout>, then the plan → approve → apply flow below.

A config edit never needs a manager rebuild. Only a new adapter id does.

The five files, worked

A minimal repository for one Mac with a shared agents module and an optional private work bundle. Every key shown is accepted by schema 1; unknown keys are refused.

base/bundle.toml The bundle: one core, a catalogue, and which parts of the checkout are sources.

schema = 1
id = "my-dotfiles"
core = "modules/core/module.toml"

# The catalogue. Nothing here is enabled; the profile selects.
[modules]
m5 = "modules/m5/module.toml"
agents = "modules/agents/module.toml"

# Only in the bundle the profile names. Paths are relative to --root.
# Needed when the checkout also holds plugin checkouts, .venv, node_modules.
[sources]
roots = ["base", "profiles"]
exclude = ["**/__pycache__", "**/.venv", "**/node_modules"]

profiles/m5-01.toml One machine. Platform and architecture must match the machine that binds it. Core is implicit.

schema = 1
id = "m5-01"
bundle = "../base/bundle.toml"
platform = "macos"
architecture = "arm64"
modules = ["m5", "agents"]

# A profile may change only values the owner exposed in policy.defaults.
[[overrides]]
resource = "m5.git-defaults"
path = "/core/editor"
value = "vim"
reason = "This machine uses its existing Vim."

base/modules/m5/module.toml Where a tool's configuration lives: one resource per output, files beside the manifest.

schema = 1
id = "m5"
platforms = ["macos"]
requires = ["agents"]

# link: HOME/.zshrc -> files/zshrc in this module
[[resources]]
id = "zsh"
kind = "link"
adapter = "fs-link/v1"
target = ".zshrc"
[resources.value]
source = "files/zshrc"

# link to a whole directory: the explicit claim is required
[[resources]]
id = "nvim"
kind = "link"
adapter = "fs-link/v1"
target = ".config/nvim"
[resources.value]
source = "files/nvim"
directory = true

# render: a typed value becomes the whole file, no template language
[[resources]]
id = "git-defaults"
kind = "render"
adapter = "git-config/v1"
target = ".config/git/config"
[resources.value.core]
editor = "nvim"
[resources.value.init]
defaultBranch = "main"
[resources.policy]
defaults = ["/core/editor"]
extensions = []

# package: accepted as data today; the binary has no package adapter yet
[[resources]]
id = "atuin"
kind = "package"
adapter = "homebrew/v1"
[resources.value]
name = "atuin"
update_policy = "rolling"
downgrade = "forbid"

schema = 1
id = "agents"
platforms = ["macos", "linux"]
requires = []

[[resources]]
id = "codex-instructions"
kind = "assemble"
adapter = "text-fragments/v1"
target = ".codex/AGENTS.md"
[resources.value]

# seed values apply only when absent, handlers are the hooks this module owns.
[[resources]]
id = "claude-settings"
kind = "merge"
adapter = "claude-settings/v1"
target = ".claude/settings.json"
[resources.value.managed]
outputStyle = "STE"
[resources.value.seed]
model = "example-model"
[resources.value.handlers.audit]
event = "PreToolUse"

Rules that bite on the first plan

  • Targets. HOME-relative and ASCII. No absolute path, no . or .. component, no leading ~, no control character. Two resources cannot claim one path, and a directory link conflicts with every claimed path below it.
  • Sources. value.source, body and friends are relative to the manifest that supplies them and must stay inside that module's directory, also through symlinks. A directory source needs directory = true.
  • Sensitive files. .claude/settings.json only through claude-settings/v1, never as a link, render or assemble. Under .ssh list only config. Put no credential in any value; a git-config/v1 value is written as given.
  • Identity. Module ids are lowercase letters, digits and internal hyphens, starting with a letter. The global resource id is <module>.<resource>. core is implicit: naming it in modules or requires is an error.
  • Changing someone else's value. An override needs the exact path in the owner's policy.defaults; a contribution needs the map in policy.extensions and a key that starts with your module id. Both need a nonempty reason. At most one override per resource and path.
  • Live checkouts. If the checkout holds plugin checkouts, .venv or node_modules, declare [sources] in the bundle the profile names. A root may not be .git. Changing [sources] changes the plan digest.
  • Limits. A document is at most 1 MiB; the loaded tree at most 20,000 entries; a generated output at most 16 MiB. plan names the three largest directories when the entry cap is exceeded.

Rules from DESIGN.md sections 3 to 5, docs/resolver.md and docs/first-run.md section 2.

Change a managed configuration implemented

Edit the dotfiles checkout, plan, approve the digest, apply. The manager never rebuilds for a config edit. Links, rendered files, assembled files and the claude-settings/v1 merge are the file classes it can write today.

Pull and apply published configuration: sync designed, not built

One command fetches the tracking ref and the module revisions it needs, validates the composition, shows one change set and applies it. The binary has no sync yet.

Update managed versions and packages: update designed, not built

One command refreshes sources, finds the latest eligible version of every managed thing, shows one diff, applies in dependency order and accounts for every participant. Package resources exist in the examples as data with a declared owner; the binary has no package adapter, so installs are by hand today.

Add a new tool, in test: try partly built

A trial installs and configures a tool without a module, records what existed before, and ends in adopt or purge. The trial record type and its storage under state/trials/ are implemented. The try, adopt and purge commands are not.

Add a new tool, permanently implemented for files

Declare the resource in a module, select the module in the profile, then run the same plan and apply flow. Removal is the same flow with the module deselected and one --allow-disruptive flag per owned output.

Remove a tool implemented for files

Removal is the same plan and apply flow with nothing selecting the outputs. The engine deletes only exact, unchanged, ledger-owned entries. Packages and runtime state are never removed by inference: today that part is by hand, and the design keeps it a reviewed plan.

Recovery: what to do after each refusal

Six flows for the refusals the happy paths can hit. Every one of these is implemented behavior; the exit codes and commands are the ones the binary prints today. A stacked column means you choose one of the alternatives.

  • you
  • dfm-cli
  • dfm-model (pure)
  • dfm-engine (writes)
  • on disk
  • refusal or branch

Plan is blocked: E_CONFLICT implemented

Something already sits at a target and the manager does not own it, or an owned output was edited. The plan still prints, and the blocker names the correction. No flag overrides it; you change the machine or the profile.

Apply refuses: E_PLAN_STALE implemented

Apply never trusts a saved plan. It plans again under the lock and compares the digest you approved. Any changed input makes the old digest useless, which is the point: you approve what will actually run.

An operation fails mid-apply implemented

The first failure stops the run. There is no rollback and no --continue: what finished stays finished and is recorded, what did not start is reported as not started. The next plan sees the finished work as current.

Apply was interrupted or the process died implemented

A caught signal ends cleanly with a receipt. An uncaught one can leave an open intent entry. The next run settles it by probing the path, and only an undecidable case needs you: check the path, then resolve the entry by hand.

Lock and state store problems implemented

The lock is an advisory flock, so a crashed holder cannot wedge it. State documents are never rewritten by a command: a damaged or newer document is yours to restore, and strays are yours to remove after reading them.

Undo: remove what the manager published implemented

Removal is an ordinary plan with one explicit flag per output. The engine deletes only an exact, unchanged, ledger-owned entry, and keeps anything modified or foreign.

What the shape says

  • Tests outnumber code. The three crates hold 27,698 lines of runtime code; tests and fixtures hold 31,056. crates/cli/tests alone is larger than any crate.
  • The model is the center of mass. dfm-model is the largest crate and the only one with no I/O. state.rs, merge.rs and plan/build.rs are its biggest files.
  • The engine owns every write. apply.rs, fsys.rs and store.rs carry the atomic-write, lock and recovery logic. failpoints.rs in its tests injects failures at named points.
  • The platform crate is tiny on purpose. 197 lines is the entire macOS surface. A Linux provider would be a sibling crate of the same shape.
  • Docs are dominated by one file. docs/roadmap.json is the exported Kaneo backlog. The human-written contract is DESIGN.md, docs/architecture.md and the per-command notes.
