# Adapters (DFM-20)

Task: DFM-20, render and assemble slice. This document records what the two generating adapters do and where it resolves or differs from [docs/architecture.md](architecture.md) (the contract). The contract wins where this document is silent. Apply is in [docs/apply.md](apply.md) and the planner in [docs/planner.md](planner.md).

Not covered here: `merge` (`claude-settings/v1`, DFM-21) and native-setting probes (DFM-20.C03). Both are deferred. See "Not built".

## What exists

| Part | Location |
| --- | --- |
| `Generator` trait, `GeneratorInputs`, input collection | `crates/engine/src/generate.rs` |
| Executor calls (inputs, generate, output hash) | `crates/engine/src/apply.rs`, `generated` |
| `git-config/v1` and `text-fragments/v1`, plan-time output hashes | `crates/cli/src/adapters/generate.rs` |
| Adapter registry: one table with each adapter's catalog entry and its generator, if any. The resolver's catalog and the `Generators` shim are both derived from it | `crates/cli/src/adapters.rs`, `registry` |
| `Operation.output_sha256`, `output_bytes`, `sets`, `fragment_dir`, `Fragment.sha256` | `crates/model/src/plan/mod.rs` |

`dfm-model` stays pure. No dependency was added. `unsafe_code` stays forbidden.

## The contract

An adapter is a `Generator`:

```rust
fn supports(&self, op: &Operation) -> bool;
fn generate(&self, op: &Operation, inputs: &GeneratorInputs) -> Result<Vec<u8>, Refusal>;
```

- `generate` is a pure function of the operation, the resource value and the inputs. It opens no file and starts no process.
- The caller reads every input. At apply time, the executor reads them descriptor-relatively, without following links, from regular files of at most 16 MiB, and compares their hashes with the plan before the adapter runs (docs/apply.md, Generator). At plan time, the CLI reads the same inputs from the loaded source snapshot and from HOME.
- `GeneratorInputs.sources` holds each source file by path. `listing` holds the names now in the fragment directory. `fragments` holds the bytes of each fragment the plan lists.
- The resource value comes from the resolved model of the plan being applied (`Generators { resolved }`). Apply plans twice and compares digests, and the digest covers the values, so the value the adapter sees is the value the reviewer approved.
- Which adapters generate is decided in one place, the `registry` table. A test requires that every `render` and `assemble` entry has a generator and that no other kind has one. `merge` has none yet (DFM-21); it is sensitive, so apply refuses it first.
- A refusal with `E_PLAN_STALE` means the inputs no longer match the plan. Apply blocks the operation. Any other refusal fails it.
- The planned output hash is computed by the same functions at plan time. Apply compares the SHA-256 of the generated bytes with `Operation.output_sha256` before the intent entry. A difference is `E_PLAN_STALE` and nothing is written.

### Layering

Architecture section 3 says adapters must not depend on `dfm-engine`. This build does not have a `ports` crate, and creating one needs a new crate and a changed dependency gate. So the `Generator` trait stays in `dfm-engine` and the adapters are in the CLI crate. `git_config` takes a model value. `text_fragments` takes `GeneratorInputs`, which is an engine type. The other engine types (`Dir`, `Sys`, `Got`) appear only in `plan_outputs`. The `toml` types `Value` and `Table` are re-exported by `dfm_model::resolve` on purpose, so the CLI can name them without a new dependency entry (docs/architecture.md section 3). Moving the trait to a `ports` crate later changes imports only.

## Data and code

Adapters are code. Everything they read is data and is read at run time.

| Change | Needs a rebuild? |
| --- | --- |
| Edit a value in `module.toml` (a Git setting, a separator, a pattern) | No |
| Edit a body file, a template or a fragment file | No |
| Add, remove or reorder fragments in a fragment directory | No |
| Select another module in the profile | No |
| Add a resource that uses an existing adapter, such as another `git-config/v1` file or another `text-fragments/v1` assembly | No |
| A new adapter id (a new kind of native file with its own rules) | Yes. It needs a `Generator`, a catalog entry in `adapters.rs` and tests. |
| A new rule inside an existing adapter (for example another Git value type) | Yes |

The adapter id and its version (`git-config/v1`) are part of the code. The value tree and the files it points to are not.

## `git-config/v1` (render)

Output: the Git config text for the resource value. Example from `examples/base/modules/core`:

```toml
[resources.value.core]
editor = "nvim"
[resources.value.init]
defaultBranch = "main"
[resources.value.fetch]
prune = true
```

becomes

```
[core]
	editor = "nvim"
[fetch]
	prune = true
[init]
	defaultBranch = "main"
```

The fixture shows only scalar values under a section. These rules are the minimum that the fixture needs plus the two forms Git ordering depends on:

1. The value is a table of sections. A section is a table.
2. A scalar entry of a section is a key. A string, an integer or a boolean is accepted. A float, a date and a nested array are refused.
3. An array of scalars is a multi-valued key. The key is written once per element, in array order. Git reads repeated keys in file order, so the array order is the order Git sees.
4. A table entry of a section is a subsection: `[includeIf."gitdir:~/work/"]` in TOML becomes `[includeIf "gitdir:~/work/"]`. A subsection holds keys only, with the same value rules. Git decodes only `\\` and `\"` in a subsection name, so the adapter escapes those two and nothing else. A newline, a tab or any other control character in a subsection name is refused (`E_MANIFEST_INVALID`).
5. Section and key names are a letter followed by letters, digits or `-`. Anything else is refused.
6. A string is always quoted. Backslash and double quote are escaped, newline and tab use `\n` and `\t`. Any other control character is refused.
7. Each line is `<tab>key = value`. The text ends with a newline unless it is empty.

**Order.** A TOML table has no order (the `toml` crate is used without its order-preserving feature, and the gate allows no new dependency). So sections, keys and subsections are written in byte order of their names, and only the elements of an array keep the author's order. Output is deterministic. A setting whose meaning depends on the order of two different keys cannot be expressed in one render resource. Use the include order instead: two `git-config/v1` files that a core `[include]` lists in the order Git must read them (docs/resolver.md, native precedence).

**Secrets.** The adapter does not read a vault. A resource with `secret_values` has another adapter. Values are written as given, so put no credential in a `git-config/v1` value.

Errors are `E_MANIFEST_INVALID` with the section or key name. The value is not repeated, except for the code point of a refused control character.

## `text-fragments/v1` (assemble)

Output: the body file, then each fragment, joined with `separator`.

Value fields: `body` (a source file), `fragments_dir` (a HOME path), `pattern` (a glob over file names) and `separator` (a string). From `examples/base/modules/agents`:

```toml
body = "files/AGENTS.md"
fragments_dir = ".codex/AGENTS.d"
pattern = "*.md"
separator = "\n"
```

Rules:

1. **Which fragments.** The adapter includes the fragments the plan lists in `Operation.fragments`. These are the files in `fragments_dir` that match `pattern` (compared without regard to case, as the planner does) and that either a selected resource produces or nobody owns (foreign). A fragment that a planned removal deletes is not listed (docs/planner.md), so a deselected producer's content never reaches the output, and one apply converges.
2. **Order.** The body is first. The fragments follow in byte order of their names. An uppercase name sorts before a lowercase name and a digit before a letter. The output is the parts joined with `separator`. Nothing is added at the end. With `separator = "\n"` and a body that ends in a newline, a blank line separates the parts.
3. **Text.** The body and each fragment must be UTF-8. Otherwise the plan has a blocker (`E_CONFLICT`) that names the file.
4. **A fragment that appeared.** If the live directory holds a matching name that the plan does not list, the adapter refuses with `E_PLAN_STALE`. A name that does not match `pattern` is ignored.
5. **Producers.** A fragment from a selected `render` or `assemble` resource is the producer's planned output. A fragment from a selected `link` resource is the producer's source file. A fragment from any other kind of producer (`merge`) is `E_GENERATOR_UNAVAILABLE`. If the producer is blocked, the consumer's blocker carries the producer's code and text ("depends on a blocked producer: ...").
6. **Foreign fragments.** A foreign fragment is read only if it is a regular file, owned by the current user, with one hard link, within 16 MiB. The planner already blocks a link, a FIFO, a directory, an unreadable file or an oversize file (docs/planner.md rule 7). Apply checks the same again with the descriptor it reads from (`Dir::read_input`): type, owner, link count, size and the hash. It also reads each source file that way. A file that fails any of these is `E_PLAN_STALE`, and the message names the path without the live hash. The planner reads sources and fragments with the same predicate, so a source that apply would refuse is a plan blocker (`E_SOURCE_UNTRUSTED` for a source, `E_CONFLICT` for a fragment) and not a surprise at apply. Hardlinked sources (`cp -al`, `rsync --link-dest`) and foreign-owned checkouts are refused for the files a generated resource reads. A link resource does not read its source, so it is not affected. The owner check is not tested with a second user.
7. **Aggregate bound.** The fragments of one assemble operation may total at most 16 MiB, the output cap. Plan and apply check the running total before each read, and the size on the descriptor before allocation. Over the cap is `E_LIMIT_EXCEEDED` (a plan blocker, or a failure at apply). Apply lists the fragment directory up to `MAX_LISTING` (50,000) entries. A longer or non-UTF-8 listing is stale, as in the planner.

Fragment content is data. The manager does not interpret, order by priority or validate the content of a fragment.

## What the plan shows

`plan` prints, under each generated file, its size and, for `git-config/v1`, the names it sets, never the values:

```
    output: 112 bytes
    sets: core.editor, credential.helper, url.ssh://git@example.test/.insteadOf
```

The JSON operation has `output_bytes` and `sets` (omitted when empty). A name is `section.key` or `section.subsection.key`, sorted, once per key. A reviewer sees a new `core.sshCommand` or `include.path` before approving. The names show what is set. They do not show the value, so the reviewer still has to read `module.toml` for it. A stale-plan difference for a changed output reads `output changed`, and a changed fragment reads `fragment <name> changed`. No hash is printed.

## Last-good output (C04)

A generation failure, a stale input or a different output hash happens before the intent entry. The staged-file publish has not started. So:

- the previous output stays byte for byte, and its mode stays;
- the ledger still names the previous hash;
- the journal has no entry for the operation;
- the operations that depend on it are `blocked`, and the run stops (docs/apply.md, Failure and accounting).

Tests: `a_generation_failure_keeps_the_last_good_output_and_blocks_dependents` (engine) and `a_malformed_fragment_blocks_the_plan_and_keeps_the_last_good_output` (CLI). Application runtime state is not touched, because the manager writes only its own outputs.

## Rerun

After the plan has `output_sha256`, an owned `update_file` whose live content and mode already equal it is `current` with action `none`. A second apply changes nothing, writes no receipt and exits 0.

## The example profile

`examples/profiles/personal-dev-01.toml` selects `personal-dev`, which requires `agents` and `desktop`. Its operations are:

| Operation | Result |
| --- | --- |
| `core.git`, `core.ssh`, `desktop.aerospace`, the `skills` leaves | Links. Apply publishes them (DFM-18). |
| `core.git-defaults` (`git-config/v1`) | Rendered and published. |
| `agents.codex-instructions` (`text-fragments/v1`) | Assembled and published. `.codex/AGENTS.d` does not exist in the example, so the output is the body. |
| `agents.claude-settings` (`claude-settings/v1`, `merge`) | Refused. It is a sensitive output, and no merge adapter exists (DFM-21). |
| `atuin`, `firstmate`, `example-secret` | `not_in_scope` (provisioning and secrets). |

The refusal is for the whole plan, as before: apply never publishes half of a profile. So the unmodified example profile is refused with `E_SENSITIVE_UNSUPPORTED` and nothing changes. I did not make the refusal per operation kind. That would let apply publish part of a profile and stop at the merge, which is the state the whole-plan gate exists to prevent. The test `the_example_profile_applies_once_the_sensitive_merge_is_left_out` copies the examples, removes the `claude-settings` resource and applies the rest in an isolated HOME. The test `the_example_profile_is_refused_whole_for_its_sensitive_merge` covers the unmodified profile. `work-01` has a link producer in `.codex/AGENTS.d`, which the planner test `a_fragment_producer_precedes_its_consumer_and_modules_are_not_barriers` plans through the assembler.

## Digest change

`Operation` gains `output_sha256`, `output_bytes`, `sets` and `fragment_dir`, and `Fragment` gains `sha256`. Each is left out of the JSON when empty. A plan with no generated file serializes as before and keeps its digest. A plan with a `render` or `assemble` operation has a new digest, because the output hash, size, setting names and fragment hashes are inside the plan.

## Decisions where the documents were silent

| Question | Choice |
| --- | --- |
| Where does the adapter get the resource value? | From the resolved model of the plan being applied, not from the plan. The plan digest covers the model, so it is the same value. |
| Value shape of `git-config/v1` | The rules above. The fixture shows only scalars. |
| Order of keys in a rendered Git config | Byte order, because the parsed TOML table has no order. Array elements keep their order. |
| Separator at the end of the output | None. The output is the parts joined, as the value field says. |
| Hash in a stale message | Not printed. The message says "changed since the plan" and names the path. |
| Which source root does apply read? | The plan's only source. A plan with generated files and more than one source is refused. The planner builds exactly one source today. |
| Plan-time generation failure | A blocker on the operation, with the generator's code. It prints no content. |
| Fragment from a `merge` producer | `E_GENERATOR_UNAVAILABLE` until DFM-21 gives that output a hash. |
| Missing fragment directory | No fragments. It is stale only if the plan listed a fragment. |
| Non-ASCII fragment names | Refused by the planner (docs/planner.md rule 1). |

## Not built

- **`merge` / `claude-settings/v1`** (DFM-21). Its output is sensitive and co-owned.
- **Native-setting probes** (DFM-20.C03). Nothing runs `git config --list` or similar. The manager does not report whether a protected setting survives every fragment. That stays the open item that docs/resolver.md names.
- **SSH and shell assemblies.** Only the two fixtures' adapters exist. A tmux, SSH or shell assembly with its own ordering rule needs its own adapter (code), or can use `text-fragments/v1` when "body plus sorted fragments" is the rule.
- **A `ports` crate.** See Layering.
- **Reload.** A published file is not reloaded (docs/apply.md). Dependents of a failed generation are blocked in the run. No reload exists to block.
- **Doctor.** `doctor` reports a generated file as `D_NA_GENERATED`. It does not compare generated content.
- **Mode drift without a declared mode.** `current` compares the mode only when the resource declares one. A file with no declared mode is judged by content alone, although apply publishes it with mode 0600.
