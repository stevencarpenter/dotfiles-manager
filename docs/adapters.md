# Adapters

This page lists the adapter registry and records what the configuration adapters (`fs-link/v1`, `git-config/v1`, `text-fragments/v1`, `claude-settings/v1`, `codex-hooks/v1`, `omlx-model-settings/v1`) do at HEAD. Apply is in [docs/apply.md](apply.md) and the planner in [docs/planner.md](planner.md).

## Registry

`crates/cli/src/adapters.rs` (`registry`) is the only place in the Rust code that names an adapter. The resolver's catalog and the `Generators` shim are both derived from it. `scripts/check_examples.py` keeps its own list for the example check.

## The `Generator` trait

An adapter that produces file content is a `Generator`:

```rust
fn supports(&self, op: &Operation) -> bool;
fn generate(&self, op: &Operation, inputs: &GeneratorInputs) -> Result<Vec<u8>, Refusal>;
```

The trait has more methods with refusing defaults: `merges`/`merge` (the co-owned merge, below), `renders`/`render` (secrets), `installs`/`probe`/`install` (packages) and `reloads`/`service_state`/`service_act` (services).

- `generate` is a pure function of the operation, the resource value and the inputs. It opens no file and starts no process.
- The caller reads every input. At apply time, the executor reads them descriptor-relatively, without following links, from regular files of at most 16 MiB, and compares their hashes with the plan before the adapter runs ([docs/apply.md](apply.md), "Generator"). At plan time, the CLI reads the same inputs from the loaded source snapshot and from HOME.
- `GeneratorInputs.sources` holds each source file by path. `listing` holds the names now in the fragment directory. `fragments` holds the bytes of each fragment the plan lists.
- The resource value comes from the resolved model of the plan being applied (`Generators { resolved }`), not from the plan. Apply plans twice and compares digests, and the digest covers the values, so the value the adapter sees is the value the reviewer approved.
- A test requires that every `render` and `assemble` entry of the registry has a generator and that no other kind has one. `merge` has no `generate` output: a test requires that every `merge` entry is sensitive and is the merge adapter.
- A refusal with `E_PLAN_STALE` means the inputs no longer match the plan. Apply blocks the operation. Any other refusal fails it.
- The planned output hash is computed by the same functions at plan time. Apply compares the SHA-256 of the generated bytes with `Operation.output_sha256` before the intent entry. A difference is `E_PLAN_STALE` and nothing is written. A stale message names the path and says "changed since the plan". It prints no hash.
- A plan with generated files must have exactly one source, and apply reads that source root. The planner builds exactly one source.

### Layering

Adapters should not depend on `dfm-engine`. This build has no `ports` crate, and creating one needs a new crate and a changed dependency gate. So the `Generator` trait stays in `dfm-engine` and the adapters are in the CLI crate. `git_config` takes a model value. `text_fragments` takes `GeneratorInputs`, which is an engine type. The other engine types (`Dir`, `Sys`, `Got`) appear only in `plan_outputs`. The `toml` types `Value` and `Table` are re-exported by `dfm_model::resolve` on purpose, so the CLI can name them without a new dependency entry. Moving the trait to a `ports` crate later changes imports only.

## Data and code

Adapters are code. Everything they read is data and is read at run time.

| Change | Needs a rebuild? |
| --- | --- |
| Edit a value in `module.toml` (a Git setting, a separator, a pattern) | No |
| Edit a body file, a template or a fragment file | No |
| Add, remove or reorder fragments in a fragment directory | No |
| Select another module in the profile | No |
| Add a resource that uses an existing adapter, such as another `git-config/v1` file or another `text-fragments/v1` assembly | No |
| A new adapter id (a new kind of native file with its own rules) | Yes. It needs an entry in `registry` (`adapters.rs`), a `Generator` when it produces content, the `scripts/check_examples.py` list, and tests. |
| A new rule inside an existing adapter (for example another Git value type) | Yes |

The adapter id and its version (`git-config/v1`) are part of the code. The value tree and the files it points to are not.

## `fs-link/v1` (link)

Value: `source` (required) and `directory` (optional boolean, default false). A `source` that names a directory is accepted only with `directory = true`, the explicit directory claim ([docs/resolver.md](resolver.md), "Directory links"). The planner then makes one link to the directory. The manager never writes through it and never deletes it recursively. `skills/v1` distributes directories by design and takes no flag. A native config linked with `fs-link/v1` is scanned for Git include directives ([docs/resolver.md](resolver.md), "Native precedence").

## `git-config/v1` (render)

Output: the Git config text for the resource value. Example from `examples/base/modules/core`:

```toml
[resources.value.core]
editor = "nvim"
[resources.value.init]
defaultBranch = "main"
[resources.value.fetch]
prune = true
```

becomes

```
[core]
	editor = "nvim"
[fetch]
	prune = true
[init]
	defaultBranch = "main"
```

The fixture shows only scalar values under a section. These rules are the minimum that the fixture needs plus the two forms Git ordering depends on:

1. The value is a table of sections. A section is a table.
2. A scalar entry of a section is a key. A string, an integer or a boolean is accepted. A float, a date and a nested array are refused.
3. An array of scalars is a multi-valued key. The key is written once per element, in array order. Git reads repeated keys in file order, so the array order is the order Git sees.
4. A table entry of a section is a subsection: `[includeIf."gitdir:~/work/"]` in TOML becomes `[includeIf "gitdir:~/work/"]`. A subsection holds keys only, with the same value rules. Git decodes only `\\` and `\"` in a subsection name, so the adapter escapes those two and nothing else. A newline, a tab or any other control character in a subsection name is refused (`E_MANIFEST_INVALID`).
5. Section and key names are a letter followed by letters, digits or `-`. Anything else is refused.
6. A string is always quoted. Backslash and double quote are escaped, newline and tab use `\n` and `\t`. Any other control character is refused.
7. Each line is `<tab>key = value`. The text ends with a newline unless it is empty.

**Order.** A TOML table has no order (the `toml` crate is used without its order-preserving feature, and the gate allows no new dependency). So sections, keys and subsections are written in byte order of their names, and only the elements of an array keep the author's order. Output is deterministic. A setting whose meaning depends on the order of two different keys cannot be expressed in one render resource. Use the include order instead: two `git-config/v1` files that a core `[include]` lists in the order Git must read them ([docs/resolver.md](resolver.md), "Native precedence").

**Case.** Git reads section names and key names without regard to ASCII case. Two section names, or two keys in one section or subsection, that differ only in ASCII case are refused (`E_MANIFEST_INVALID`). Subsection names are case-sensitive and may differ only in case.

**Secrets.** The adapter does not read a vault. A resource with `secret_values` has another adapter. Values are written as given, so put no credential in a `git-config/v1` value.

Errors are `E_MANIFEST_INVALID` with the section or key name. The value is not repeated, except for the code point of a refused control character.

## `text-fragments/v1` (assemble)

Output: the body file, then each fragment, joined with `separator`.

Value fields: `body` (a source file), `fragments_dir` (a HOME path), `pattern` (a glob over file names) and `separator` (a string). From `examples/base/modules/agents`:

```toml
body = "files/AGENTS.md"
fragments_dir = ".codex/AGENTS.d"
pattern = "*.md"
separator = "\n"
```

Rules:

1. **Which fragments.** The adapter includes the fragments the plan lists in `Operation.fragments`. These are the files in `fragments_dir` that match `pattern` (compared without regard to case, as the planner does) and that either a selected resource produces or nobody owns (foreign). A fragment that a planned removal deletes is not listed ([docs/planner.md](planner.md), "Removal"), so a deselected producer's content never reaches the output, and one apply converges. A missing fragment directory holds no fragments.
2. **Order.** The body is first. The fragments follow in byte order of their names. An uppercase name sorts before a lowercase name and a digit before a letter. The output is the parts joined with `separator`. Nothing is added at the end. With `separator = "\n"` and a body that ends in a newline, a blank line separates the parts.
3. **Text.** The body and each fragment must be UTF-8. Otherwise the plan has a blocker (`E_CONFLICT`) that names the file.
4. **A fragment that appeared.** If the live directory holds a matching name that the plan does not list, the adapter refuses with `E_PLAN_STALE`. A name that does not match `pattern` is ignored.
5. **Producers.** A fragment from a selected `render` or `assemble` resource is the producer's planned output. A fragment from a selected `link` resource is the producer's source file. A fragment from any other kind of producer (`merge`) is `E_GENERATOR_UNAVAILABLE`, because a merged file has no content hash by design. If the producer is blocked, the consumer's blocker carries the producer's code and text ("depends on a blocked producer: ...").
6. **Foreign fragments.** A foreign fragment is read only if it is a regular file, owned by the current user, with one hard link, within 16 MiB. The planner already blocks a link, a FIFO, a directory, an unreadable file or an oversize file ([docs/planner.md](planner.md), rule 7). Apply checks the same again with the descriptor it reads from (`Dir::read_input`): type, owner, link count, size and the hash. It also reads each source file that way. A file that fails any of these is `E_PLAN_STALE`, and the message names the path without the live hash. The planner reads sources and fragments with the same predicate, so a source that apply would refuse is a plan blocker (`E_SOURCE_UNTRUSTED` for a source, `E_CONFLICT` for a fragment) and not a surprise at apply. Hardlinked sources (`cp -al`, `rsync --link-dest`) and foreign-owned checkouts are refused for the files a generated resource reads. A link resource does not read its source, so it is not affected. The owner check is not tested with a second user.
7. **Aggregate bound.** The fragments of one assemble operation may total at most 16 MiB, the output cap. Plan and apply check the running total before each read, and the size on the descriptor before allocation. Over the cap is `E_LIMIT_EXCEEDED` (a plan blocker, or a failure at apply). Apply lists the fragment directory up to `MAX_LISTING` (50,000) entries. A longer or non-UTF-8 listing is stale, as in the planner.

Fragment content is data. The manager does not interpret, order by priority or validate the content of a fragment.

## `claude-settings/v1` (merge)

Output: `.claude/settings.json`, as a JSON object. The file is co-owned: the application and the user write it too, and it can hold credentials in keys the manager does not know. Its class is `sensitive`.

Value fields, as in `examples/base/modules/agents` (that example declares no handler; `audit` here shows the handler shape):

```toml
[resources.value.managed]
outputStyle = "STE"
[resources.value.seed]
model = "example-model"
[resources.value.handlers.audit]
event = "PreToolUse"
type = "command"
argv = ["audit", "--quiet"]
matcher = "Bash"   # optional: the matcher of the hook group
timeout = 20       # optional: seconds, a positive integer
[resources.policy]
defaults = ["/managed/outputStyle"]
extensions = ["/handlers"]
```

`handlers` is optional: a value with only `managed` (and `seed`) merges settings and adds no hook.

Optional value fields (DFM-48), shortened from `examples/base/modules/claude-base`:

```toml
[resources.value]
append = ["/sandbox/filesystem/allowWrite"]
fragments_dir = ".claude/settings.d"
pattern = "*.json"
[resources.value.managed.sandbox.filesystem]
allowWrite = ["~/.cache/example-tool", "~/projects/example"]
```

`append` lists JSON pointers into the settings file. Each pointer must name an array under `managed` (case-sensitive). Otherwise the resource is `E_MANIFEST_INVALID`, because a mistyped pointer would turn append into replace and lose the user's items. `/hooks` is refused. `fragments_dir` and `pattern` go together: declare both or neither.

`append` is a field of the value, beside `managed`, not of `[resources.policy]`. The resolver accepts only `defaults` and `extensions` in `policy` ([docs/resolver.md](resolver.md)), because a policy is authority over overrides, not adapter input. The resolver applies `policy.defaults` and `policy.extensions` to any pointer of the value (an overlay can change a default, add a handler, or change `/managed/enabledPlugins/example-tools@example-marketplace`). The adapter reads the resolved value. A config edit needs no rebuild.

**Mapping rule.** `managed` and `seed` act on the settings file at any depth, and a policy pointer addresses the same resolved value: `/managed/outputStyle` is the field `outputStyle` of `managed`, which sets the top-level key `outputStyle`. A managed table merges into the live table (rule 1). A key in `managed` that is empty or has a control character, at any depth, is `E_MANIFEST_INVALID`: the ledger cannot name it, so an edit of it would never be detected. The fixture `examples/base/modules/claude-base` shows every shape of a full base settings file: `env`, `permissions`, `statusLine`, `enabledPlugins`, `skillOverrides`, `extraKnownMarketplaces`, flags, an `append` array, seeds and seven handlers.

**Fixed destination.** The adapter writes `.claude/settings.json` only. A resource of this adapter with any other `target` is `E_MANIFEST_INVALID` at resolution (`TargetRule::Fixed`), with the fix text `set the target to .claude/settings.json`. The destination is pinned so a module cannot point the sensitive merge at another file.

### Merge rules

The base is the live document. The merge changes only what the module declares.

1. **Managed.** The manager sets each declared leaf and keeps what else the live file holds.
   - A declared table merges into the live table at any depth. A managed leaf wins. A leaf the manager does not declare stays, so a plugin the user enabled in Claude Code survives.
   - A declared array or scalar replaces the live value, like `jq` `*`, with one exception: an `append` array (rule 1a). A user item in a managed array without `append` is lost. List the pointer in `append` to keep it.
   - A declared `false` is an explicit disable and is written as `false`. TOML has no null, so a JSON `null` cannot be declared.
   - A declared table over a live value that is a scalar or an array is `E_CONFLICT`. So is a declared scalar or array over a live table, which would discard a foreign subtree. The manager does not rewrite a foreign shape. The message names the path and no content. A live `null` counts as absent. The nix merge replaces the value for most keys and fails for `sandbox.filesystem`. A refusal never loses user data.
   - **Append (1a).** A key listed in `append` keeps the live array. The manager adds each unique declared item that is not already in it, at the end, in declared order. A live value of another shape is `E_CONFLICT`. An absent array is created from the declared items. The manager records the items it added in the ledger (`coowned.appended`, [docs/state.md](state.md)), keyed by the pointer and the SHA-256 of the item. The next merge removes a recorded item that is no longer declared, and a deselect removes all recorded items. An item the user added is never removed. An identical item that was already in the file before the first write stays the user's, except at the approved take-over, as for hook entries (rule 4). A user who deletes a recorded item gets it back. An array that a removal emptied is removed, and so is every parent table the removal emptied.
2. **Seed.** Each leaf of `seed` is set only where the live file has nothing (or `null`), at any depth. A live value, including `false`, is never overwritten. A seed table merges into a live table, so `permissions.defaultMode` is set only when the live file has no such key. Seeds apply after managed values, so a key in both `managed` and `seed` is managed, and a seed leaf fills a gap in a table the manager also sets.
   - **Fragments (2a).** The value can declare `fragments_dir` and `pattern`. The files in the directory that match the pattern are JSON objects. They merge over the declared managed values in byte order of their names, before the live merge (rule 1 then applies to the layered result). A later name wins. Tables merge, and arrays and scalars replace, as for `jq` `*` in the nix merge. At an `append` pointer two arrays concatenate with unique items, so a fragment adds to a declared list. A fragment cannot set `hooks`: hooks are declared as handlers. A fragment that is not valid JSON, is not an object, sets `hooks`, or holds a key that is empty or has a control character at any depth is `E_CONFLICT` (such a key cannot be compared leaf by leaf, so an edit of it would go unseen). The message names the fragment, the error category, the line and the column, and no content. The operation is blocked, nothing is written and the last good file stays. The nix merge skips a bad fragment instead. The manager blocks, because a skipped fragment would silently change which managed values apply. The manager does not order fragment content by priority beyond the name. A fragment is read as the planner and apply read any input (`Dir::read_input`): a regular file of the user with one hard link, within the 16 MiB bound shared with all fragments of the operation. A fragment writable by group or others (`mode & 0o022`) is `E_CONFLICT` with the fix `chmod go-w`, because its keys can run code. The planner's set decides which fragments a merge layers: files that match and that nobody removes, plus the source files of selected link resources ([docs/planner.md](planner.md), "Fragments for a merge").
3. **Handlers.** Each handler is one hook group `{"hooks":[{"type":"command","command":"<argv>"}]}` added to the array `hooks.<event>`. A handler can set `matcher`, which becomes the `matcher` of the group (an empty string matches everything; a control character is refused), and `timeout`, which becomes the `timeout` of the hook (an integer from 1 to 3600 seconds). A group without a declared `matcher` has none. The nix base file puts two commands in one group (`SubagentStop`). Declare two handlers for that: the manager adds two groups, which Claude Code runs the same way. `argv` is joined into one shell command. A word is single-quoted unless it only holds `A-Za-z0-9_@%+=:,./-`. A word is also quoted when it starts with `=` (zsh expands it) or `%` (a job spec), or looks like `NAME=value` (an environment assignment in command position). A word that starts with `${HOME}` keeps that reference live in double quotes, so a hook finds the home directory on each machine. Only the type `command` is built. Any other type is `E_MANIFEST_INVALID` with fix text, because the manager cannot reverse it safely.
4. **Owned list.** The ledger records, for each handler the manager added, its id, its event and the SHA-256 of the entry it declared (declared content, not live content), as `coowned.entries[{id, key, sha256}]`. `key` is the list the entry sits in (the hook event); the name is generic so another co-owned list can use it. The ledger holds one record for each distinct (event, entry hash): two handlers with identical content share one live copy and one record. The next merge removes an owned entry whose handler is gone or changed, matching by that hash, so a foreign entry is never touched. It adds each declared entry unless an identical one is already in the array. A user who deleted an owned entry gets it back, because the manager owns it. The ledger records ownership only for an entry the manager added, or one it already recorded. An identical entry that was in the file before the manager first wrote stays the user's, so a later `retire` never removes it, with one exception: the approved take-over. The first write into an existing file with no ledger entry needs `--allow-adopt`, and that approval covers every identical entry already in place. They are recorded as owned, because after an interrupted first merge (an `unknown` outcome that an operator closed with `state resolve --as failed`) the manager's own entries sit in the file and nothing tells them from a user's copy. A later `retire` removes them.
   - **Equivalent hooks (4a).** Before the manager adds a handler it checks whether the event already runs the same command. The check reads the live commands as a shell reads words (single and double quotes, backslash; no expansion; words split on a space, a tab or a newline only, so a no-break space stays inside its word). It treats `~/`, `$HOME/`, `${HOME}/` and the absolute HOME path at the start of a word as one spelling, but only where the shell would expand them: `~` and `$HOME` when unquoted, `$HOME` also inside double quotes. A single-quoted or backslash-escaped `~` or `$HOME` is literal text and another command, and so is a token that is only partly quoted (`"$"HOME/x`, `$HO"ME"/x`, `~"/x"`): the whole leading token must be written as one unit. The identity of a hook is its type `command`, the words of its command and the `matcher` of its group. The `timeout` and any other hook in the group do not matter, so a group the nix merge wrote with two hooks counts as holding both. An equivalent hook is not duplicated. The manager does not record an equivalent hook as owned, not even at the take-over (only an exact copy is), because a retire matches by the hash of the declared entry and could otherwise remove a group that holds foreign hooks. A command with an unclosed quote is compared as raw text.
5. **Retire.** When the resource is no longer selected, the manager removes only the owned entries (the plan action `retire`). Managed and seeded values stay, every foreign key and hook stays, and the file is never deleted. An event array or the `hooks` object that the removal emptied is removed. One that was already empty is left alone. `retire` needs no approval beyond `--yes-plan`.
6. **Foreign shapes.** If `hooks` is not an object, or `hooks.<event>` is not an array, the merge stops with `E_CONFLICT` and fix text. `managed.hooks` and `seed.hooks` are refused: hooks are declared as handlers. Foreign hook groups keep their `matcher` and every handler type (`command`, `prompt`, `agent`, `http`, `mcp_tool`). The manager removes an owned entry by its recorded hash only. The nix merge removes by command marker, so it also sweeps old hooks the manager never added. The manager does not: a hook it did not record is the user's.
7. **Normalized formatting.** A merge or retire that changes no value keeps the live bytes: when the result equals the live document as JSON (object key order, spacing, string escapes and the spelling of a whole number, `1` or `1.0`, do not count), nothing is written. An application that rewrites the file in its own key order therefore does not make the resource `planned` again (DFM-68). Any other output is the document re-serialized with sorted keys, a 2-space indent and a final newline. Comments are not part of JSON. Key order, spacing and number spelling are then not preserved. Integers that fit 64 bits and finite floats are kept by value. A float with no fractional part in the `i64` range (`1.0`, `1e3`) is the same value as that integer when the manager compares a live leaf with its record and when it decides whether the merge changes the file, so the spelling alone is never a foreign edit and never a change. An integer literal outside the 64-bit range in the live file is `E_CONFLICT`, because it would be rewritten as a float; the manager writes nothing until the file is fixed. A duplicate key in the live file keeps the last value (the `serde_json` rule; `JSON.parse` keeps the last as well). A file whose values do not change keeps both copies in its bytes.
8. **Absent and invalid input.** An absent file is `{}`. A file that is not valid JSON, or is JSON but not an object, blocks with `E_CONFLICT` and writes nothing. The message gives the error category, line and column, and no content.

### Sensitive policy

- The plan, the receipt, the journal, `--json`, the table and `doctor` hold no live content, no hash of the live file and no salted hash.
- The plan holds, for this operation: the path, the mode (0600, or 0644 for `omlx-model-settings/v1`), the setting names (`sets`, names only), the fragments (`fragments`, names and origin) and `managed_sha256`. That is the SHA-256 of the canonical JSON of the declared `managed` values. The module declares them, so the digest is not secret. It shows a reviewer that the declared set changed. It says nothing about the live file. A setting name is the dotted path from the top of the file to a leaf, such as `env.EXAMPLE_FEATURE_FLAG`. The names include the keys of the fragments.
- A fragment can hold credentials, so the fragments of a sensitive merge are sensitive themselves: no plain hash of a fragment is printed or stored. The `fragments:` precondition of the operation carries a salted content token for each fragment (the salted SHA-256 of the name and the content, with `state/salt`). The token lands in the plan JSON (`preconditions[].state`) and so in the plan digest, which makes a changed fragment stale. It is never printed by the text plan, a stale report (which says `fragment content changed`), the receipt, the journal, `doctor` or `status`, and it is not stored in the ledger. A merge that has fragments needs `state/salt` at plan time: without it the plan blocks with `E_STATE_INVALID` and the fix "run bind again with the same profile and machine id", which creates the salt ([docs/state.md](state.md), "Documents"). A merge without fragments needs no salt at plan time. Assembly fragments (`text-fragments/v1`, normal class) keep their plain hashes.
- `output_sha256` stays unset: a sensitive output has no content hash. No hash of the live settings file exists anywhere.
- `ledger.json` holds a per-machine salted hash of the managed fields as the manager last wrote them (`coowned.managed_hash`, per leaf in `coowned.leaves`), and the owned handler entries. The salt is 32 random bytes in `state/salt`. No other file holds the salted hash.
- A parse error, a conflict and a stale-input message never repeat a byte of the live file.

### Limits and hardening

- **Ledger bound.** One merge records at most 10,000 managed leaves, hook entries and appended items together (`dfm_model::merge::MAX_RECORDED`). A merge over the bound is `E_LIMIT_EXCEEDED` at plan and apply, and nothing is written, so the live file never changes without its ledger entry.
- **Fragment recheck.** Plan time reads the fragments in `merge_facts`, as apply does: below HOME without following a link, regular, one hard link. Apply reads the planned list again and compares the salted content token of each fragment, so a fragment swapped after the re-plan under the lock is `E_PLAN_STALE`. A matching name in the directory that the plan did not list is `E_PLAN_STALE` too.
- **Lost salt.** A missing or unusable salt while the ledger records a salted hash is a hard state error. The recovery is in [docs/state.md](state.md), "Documents".
- **The salted hash is not an HMAC.** `salted()` is SHA-256 of the salt, a tag and the data. A length-extension attack cannot yield a valid JSON view, so this is accepted.
- **A scalar over a manager-written table.** If a later module declares a scalar where the manager wrote a table, the merge is `E_CONFLICT` until someone repairs the file by hand. The manager does not discard a foreign subtree.

### Conflict detection

At plan time and again at apply time the manager reads the live file and compares only the managed fields.

1. The live managed view is the canonical JSON of the declared managed leaves, with the fragments merged in, as the live file holds them at the same paths. A leaf that is absent is left out. A foreign leaf beside a managed one is not part of the view, so a plugin the user enabled or a sandbox path the user added is no edit. The items of an `append` array are not part of the view either: the manager restores a deleted item, as it does for a hook entry. A table that holds none of the declared leaves is left out.
2. Its salted hash is compared with the ledger record.
3. If the ledger has no entry for this resource and path and the file exists, the first write is a take-over. It is a planned operation that needs `--allow-adopt '<id>'` (next section). An absent file needs no flag.
4. If the hashes are equal, the manager may write.
5. If they differ and the live managed view is not already equal to the declared values, a managed field was changed outside the manager. The operation is `E_CONFLICT`, nothing is written, and the fix text says: restore the declared value in the file, or declare the edited value in the module so the manager adopts it. No value is printed. If the live managed view already equals the declared values, nothing is overwritten and the write is allowed.
6. A managed key that the user removed counts as an edit.
6a. The comparison is leaf by leaf (DFM-48), with `coowned.leaves`. Only a leaf that both the ledger and the module name now is compared, so a dropped key or a removed fragment is not taken for a hand edit, and a key that was added has nothing to compare. A hand edit of a leaf that stays managed is still `E_CONFLICT`. The whole-view hash is not consulted for the check, because it covers the old key set: a key renamed in one source update (one removed, one added) applies in one step. A ledger record without leaf hashes has nothing to compare, and the first write records them. A hook entry or appended item is removed once per ownership record, and the records are unique (the validator refuses a repeat): an identical copy that the user added stays. A handler id that is empty or holds a control character is `E_MANIFEST_INVALID` when the resource is read, before any write.
7. If the file is absent while the ledger has an entry (the user deleted it), there is nothing to compare. The plan is a create: the merged document is built from `{}` and the salted hash is recorded again.

Plan and apply use one pure function for the comparison, `dfm_model::merge::check_foreign` (built on `foreign_edit`). `classify` adds the merge and the `current` test for the plan.

An entry of another resource in the ledger for the same path blocks before the file is read. A symlink, a file of another owner, a hard-linked file or a file over 16 MiB is refused. A file open to group or others (a mode that has any bit in `0077`) is refused with `E_CONFLICT` and the fix `chmod 600`. The manager does not change a mode it did not set. The published file always has mode 0600.

### Take over an existing file

Owner-delegated decision (2026-10-11). The first write into an existing settings file that has no `coowned` ledger entry for this resource is the operation `update_file` with `takeover = true`. Its effect text reads `take over managed fields of an existing file <path> (sensitive: destination and mode only); foreign keys are kept; hand edits of managed fields are overwritten`. Apply refuses it without `--allow-adopt '<operation-id>'` (`E_ADOPT_UNAPPROVED`, exit 3, nothing written). No prompt exists, so the per-operation flag stands in for a confirmation that names the destination, as for link adoption. The approval is recorded in the receipt as `how = allow_adopt`. An absent file is a create and needs no flag. After the first write the ledger has the entry, and later runs need no flag. A deleted file with a ledger entry is a create too.

### What the plan shows for a merge

```
  planned agents.claude-settings@.claude/settings.json [agents] merge into .claude/settings.json (sensitive: destination and mode only): managed values set, seeds only if absent, owned handlers added; foreign keys and hooks stay: 3 setting(s), 1 handler(s); live content is not shown
    managed: sha256:<digest of the declared managed values>
    sets: model, outputStyle, sandbox.filesystem.allowWrite
    fragments: 10-local.json, 20-later.json
```

The `fragments:` line appears when the resource declares a fragment directory and it holds fragments. It lists names in merge order. The plan JSON lists each as `{name, origin, sha256}`, and `sha256` is always null for a merge ("Sensitive policy"). `origin` is `foreign` for a file nobody selects and `selected:<resource>` for a file a selected link resource puts there. The `sets` and `fragments:` lines are for people. Nothing reads them back.

`current` means the merged result equals the live document as JSON (rule 7) and the ledger already records the same salted hash and the same owned entries. A file that is already correct but has no ledger entry is `planned`: apply records ownership and publishes nothing. A deselected resource shows `retire N owned handler(s)`. `doctor` shows a healthy merge output as `N/A` (`D_NA_SENSITIVE`). A foreign edit or a malformed file is the plan's `E_CONFLICT`, shown as `ERROR` ([docs/doctor.md](doctor.md)).

### Check-then-act limit

Apply reads the live file again under the writer lock and builds the result from those bytes, so an application edit made after `plan` and before apply is merged, not lost. The file is staged in the same directory (0600, `fsync`) and moved with `renameat`. Immediately before the rename, apply compares the file's identity with the identity captured at the re-read: device, inode, size, modification time and change time. A replaced or rewritten file fails the check with `E_CONFLICT`, the staged file is removed and the live file stays as the application left it. No whole-file hash exists to compare.

The check and the rename are two system calls. A write by another process between them is not detected, and the rename then replaces that write with a merge of the older content. This is the same check-then-act limit as `replace_link` and `update_file` ([docs/apply.md](apply.md)). A manager lock is not a lock on the application. Close the application, or run apply when it is idle, to remove the window.

## `codex-hooks/v1` (merge)

Output: `.codex/hooks.json`. Codex reads its hooks from this file in the shape of the `hooks` object of the Claude settings: `{"hooks": {<event>: [{"matcher"?, "hooks": [{"type", "command", ...}]}]}}`. Other tools (plugins, `codebase-memory-mcp`, `impeccable`) add their own groups to it. The adapter replaces the `jq` step `codex_hooks_merge` of `~/.dotfiles/scripts/hooks-sync.sh`.

It is the `claude-settings/v1` merge with handlers only. The value has one field, `handlers`, with the handler shape above:

```toml
[[resources]]
id = "codex-hooks"
kind = "merge"
adapter = "codex-hooks/v1"
target = ".codex/hooks.json"
[resources.value.handlers.hippo]
event = "SessionStart"
type = "command"
argv = ["${HOME}/.local/share/hippo-brain/shell/claude-session-hook.sh"]
[resources.policy]
extensions = ["/handlers"]
```

Everything in the `claude-settings/v1` section applies except `managed`, `seed`, `append` and fragments, which the schema does not accept: the fixed destination (any other target is `E_MANIFEST_INVALID`), class `sensitive`, mode 0600, the ledger records (`coowned.entries`), the take-over with `--allow-adopt`, the re-read under the lock, the identity-guarded rename, the retire of owned entries only, and malformed JSON as `E_CONFLICT` with the last good file kept. A foreign hook entry of any type or shape is carried over by value, with every key it holds (`command_windows`, `commandWindows`, `statusMessage`, `timeout`, `prompt`, `url`). A hook that runs the declared command with another home spelling (`/Users/<you>/...` for `${HOME}/...`) is the user's: it is not duplicated and not owned, so a retire never removes it. Tests: `crates/cli/tests/codex_hooks.rs`.

MCP configuration and skill fan-out stay with `mcp_sync` (DFM-21, revision 2026-10-20). The manager neither ports nor invokes it.

## `omlx-model-settings/v1` (merge)

Output: `.omlx/model_settings.json`, the per-model settings of the oMLX app: `{"version": 1, "models": {<model id>: {...}}}`. The app's admin UI, profiles and context benchmark rewrite the whole file from memory through an atomic rename, so a link or a one-shot script does not hold. The adapter merges the declared per-model leaves and keeps every other model and key.

It is the `claude-settings/v1` merge with `managed` only (required). The value declares leaves under `models`:

```toml
[[resources]]
id = "omlx-models"
kind = "merge"
adapter = "omlx-model-settings/v1"
target = ".omlx/model_settings.json"
[resources.value.managed.models."Qwen3.6-35B-A3B-Abliterated-Heretic-MLX-4bit"]
enable_thinking = false
forced_ct_kwargs = ["enable_thinking"]
trust_remote_code = false
```

What differs from `claude-settings/v1`:

- **Mode 0644.** The app writes the file with mode 0644 (its umask), so the adapter publishes 0644 and accepts a live file whose group and other bits stay within 0644 (`merge::mode_for`). A file writable by group or others is `E_CONFLICT` with `chmod 644` as the fix. Every other merge keeps 0600.
- **The server settings stay out.** `.omlx/settings.json` holds the server's credentials. The fixed target keeps the merge away from it: no adapter reads or writes it, and a module that names it is `E_MANIFEST_INVALID`. The test `the_server_settings_file_never_reaches_any_output_or_state_file` plants a token there and checks every output and state file.
- **Restart.** oMLX reads the file only at start, and each save rewrites it from memory. A write while the app runs is therefore lost at its next save unless the app restarts first. Declare the `omlx-app/v1` service with `config = [".omlx/model_settings.json"]` ([docs/lifecycle.md](lifecycle.md)) and run `dfm sync --restart <resource-id>` (or `dfm services --restart <resource-id> --allow-disruptive <operation-id>`) after a change. The restart is never inferred. It sends SIGTERM to the `omlx-server` pid that the app's control socket names, and the app starts a new server that reads the file. `omlx-cli restart` is not used: with oMLX 0.7.0 it makes the app exit and leaves an orphaned server (docs/lifecycle.md).

The class stays `sensitive` (no content hash, salted managed-field hash in the ledger), the destination is fixed, and the rules for take-over, conflicts, key order (a JSON-equal file is `current`, DFM-68) and malformed JSON are those of `claude-settings/v1`. Tests: `crates/cli/tests/omlx.rs`.

## What the plan shows for a generated file

`plan` prints, under each generated file, its size and, for `git-config/v1`, the names it sets, never the values:

```
    output: 112 bytes
    sets: core.editor, credential.helper, url.ssh://git@example.test/.insteadOf
```

The JSON operation has `output_bytes` and `sets` (omitted when empty). A name is `section.key` or `section.subsection.key`, sorted, once per key. A reviewer sees a new `core.sshCommand` or `include.path` before approving. The names show what is set. They do not show the value, so the reviewer still has to read `module.toml` for it. A stale-plan difference for a changed output reads `output changed`, and a changed fragment reads `fragment <name> changed`. No hash is printed. An owned generated file that is already current plans nothing ([docs/planner.md](planner.md), "Known limits").

## Last-good output (C04)

A generation failure, a stale input or a different output hash happens before the intent entry, so the staged-file publish has not started. The previous output stays byte for byte with its mode, the ledger still names the previous hash, the journal has no entry for the operation, and the dependent operations are `blocked` ([docs/apply.md](apply.md), "Failure and accounting"). Application runtime state is not touched, because the manager writes only its own outputs.

Tests: `a_generation_failure_keeps_the_last_good_output_and_blocks_dependents` (engine) and `a_malformed_fragment_blocks_the_plan_and_keeps_the_last_good_output` (CLI).

## Not built

- **Other co-owned destinations**: MCP server configuration files, Codex `config.toml` and any reverse transformation of them. `mcp_sync` keeps them (DFM-21). An unsupported reverse transformation stays an explicit blocker with fix text, as for a handler of another type.
- **A JSON `null` disable.** TOML cannot express it. Only `false` and other TOML values are declarable.
- **Forged ledger.** The ledger is not authenticated. A same-user edit of `coowned.entries` can make `retire` remove a hook entry whose hash it names. The same holds for `coowned.appended`: the validator accepts only canonical pointers outside `hooks`, but a deselected resource has no declared pointers to check against, so a forged pair can remove an array item with the hash it names. The validator refuses a repeated record, so a forged ledger cannot remove more copies than it names distinct hashes. This is the same limit as for removals ([docs/apply.md](apply.md), "Known limits").
- **Hand edit on the first merge.** A hand edit of a managed field is overwritten by the first write into an existing file. The `--allow-adopt` flag and the plan text say so before it happens.
- **Nix capability variants.** The nix merge builds `enabledPlugins` and `SessionStart` hooks from the capability set of the host. The manager has no capability input for a merge. Express a variant as an overlay or a second module selected by the profile.
- **Sweeping by command marker.** The nix merge also removes hooks it never added if the command contains a marker (retired tools). The manager removes only entries its ledger records. A retired hook from before the first manager write stays until the user removes it.
- **Key order.** The nix merge keeps the live key order. The manager writes sorted keys when a value changes, and leaves a file that already holds the merged values in its own order (rule 7).
- **Removal of an emptied parent table you declared.** A managed table that the manager declares stays even if every declared leaf is later dropped: only `append` removals prune the tables they empty.
- **Fragments from generated producers.** A merge layers fragments from link resources and foreign files only. A fragment from a `render`, `assemble` or `merge` resource is `E_GENERATOR_UNAVAILABLE`.
- **Capture** (adopting a live file into the sources). The merge never writes the sources.
- **Native-setting probes** (DFM-20.C03). Nothing runs `git config --list` or similar. The manager does not report whether a protected setting survives every fragment ([docs/resolver.md](resolver.md), "Native precedence").
- **SSH and shell assemblies.** Only the fixtures' adapters exist. A tmux, SSH or shell assembly with its own ordering rule needs its own adapter (code), or can use `text-fragments/v1` when "body plus sorted fragments" is the rule.
- **A `ports` crate.** See Layering.
- **Reload.** A published file is not reloaded ([docs/apply.md](apply.md), "Publication and reload").
- **Doctor regeneration.** `doctor` compares a generated file by its recorded fingerprint, like any owned file. It does not regenerate the content to compare it.
- **Mode drift without a declared mode.** `current` compares the mode only when the resource declares one. A file with no declared mode is judged by content alone, although apply publishes it with mode 0600.
