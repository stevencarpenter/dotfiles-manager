# Upgrade

The upgrade step of `dfm sync` (DFM-31; the `mise`, `rustup`, `uv` and `npm` updaters are DFM-85): after the four scopes, each updater the profile declares runs through its own owner's updater and ends in one status. This document describes the behavior at HEAD.

| Part | Location |
| --- | --- |
| `Updater`, the fixed set | `crates/model/src/updater.rs` |
| The profile key `updaters` | `crates/model/src/resolve/docs.rs` (docs/resolver.md, rule 16) |
| One updater: `run`, `preview`, `Row`, the source check `trust_notes`; the shared outdated-list flow `roll` (mise, rustup, npm) | `crates/cli/src/adapters/updater.rs` |
| Source identities and grants | `crates/model/src/lock.rs` (`source_identity`, `Grants`) |
| The step in sync: `upgrade`, `upgrade_preview` | `crates/cli/src/sync_cmd.rs` |
| Doctor's `D_UPGRADE` row | `crates/cli/src/doctor_cmd.rs` |
| Tests with look-alike updaters | `crates/cli/src/adapters/updater.rs` (unit), `crates/cli/tests/sync.rs` (the upgrade section) |

## Declaring the updaters

```toml
# profiles/personal-mac.toml
updaters = ["claude", "codex", "opencode", "brew", "skills", "agents"]
```

The names come from a fixed set built into the manager. A document cannot add a command, so a commit pulled from GitHub cannot make sync run a program the manager does not know. The updaters run in the declared order, one at a time. An absent or empty list runs none.

A manager built before this key refuses a profile that has it (`E_FIELD_UNKNOWN`). Declare `updaters` only after every machine that uses the profile runs a manager that knows it.

## The fixed set

| Name | Commands | Version before and after | Owner path |
| --- | --- | --- | --- |
| `agents` | working copy: `git status --porcelain`; managed copy: `git status --porcelain`, `git rev-parse --abbrev-ref HEAD`, `git config --get branch.<branch>.remote` and `.merge`, `git remote get-url <remote>`, `git fetch <remote>`, `git rev-list --count @{u}..HEAD`, `git pull --ff-only <remote> <merge>`; then `scripts/install-agent-registry.sh <copy>` | `git rev-parse --short HEAD` of the copy | the working copy `~/projects/agents` or the managed copy `~/.local/share/agent-registry`; the script in the bound checkout (`--root` or the binding's root) |
| `brew` | `brew update`; `brew outdated --json=v2`; `brew upgrade --formula <names>`; `brew upgrade --cask <names>`; `brew outdated --json=v2` | each outdated name's installed and newest version | `brew` on the provider path (`/opt/homebrew/bin`) |
| `checkouts` | per declared checkout, in this order: `git rev-parse --short HEAD`, `git status --porcelain`, `git rev-parse --abbrev-ref HEAD`, `git config --get branch.<branch>.remote`, `git config --get branch.<branch>.merge`, `git remote get-url <remote>`, `git fetch <remote>`, `git rev-list --count @{u}..HEAD`, `git pull --ff-only <remote> <merge>`, `git rev-parse --short HEAD` | the first and last `git rev-parse --short HEAD` of each checkout, in its note | `git` on the provider path; each `git-checkout/v1` path under HOME |
| `claude` | `claude update` | `claude --version` | `~/.local/bin/claude` |
| `codex` | `codex update` | `codex --version` | `~/.codex/packages/standalone/current/bin/codex` |
| `opencode` | `opencode upgrade` | `opencode --version` | `~/.opencode/bin/opencode` |
| `skills` | `mise exec -- npx skills update` | none | `mise` on the provider path |
| `mise` | `mise ls --installed --json`; `mise install`; `mise ls --installed --json`; `mise outdated --json`; `mise upgrade`; `mise outdated --json` | each outdated tool's installed and newest version | `mise` on the provider path |
| `rustup` | `rustup check`; `rustup update`; `rustup check` | each toolchain with an update, and rustup itself | `~/.cargo/bin/rustup` |
| `uv` | `uv tool list`; `uv tool upgrade <name>` per tool; `uv tool list` | each tool's version in the listing | `uv` on the provider path; the tools under `~/.local/share/uv/tools` |
| `npm` | `npm ls -g --depth=0 --json`; `npm outdated -g --json`; `npm update -g <names>`; `npm outdated -g --json` | each outdated package's installed and wanted version | `npm` on the provider path |
| `side-channels` | `just --justfile <root>/Justfile --working-directory <root> sync-side-channels` | none | `just` on the provider path; the `Justfile` in the bound checkout |

- **agents** installs the agent registry (`stevencarpenter/agents`, DFM-25.C09). When `~/projects/agents/pyproject.toml` exists, the working copy is used as it is: it is never fetched or pulled, the row shows its revision, and a dirty copy has the note `working copy <path> has uncommitted changes; not pulled`. Otherwise the managed copy `~/.local/share/agent-registry` is fast-forwarded. Before any change, a managed copy that is missing (no `.git`), dirty (`git status --porcelain` prints a line), without an upstream branch (no `branch.<branch>.remote` or `.merge`; checked before the fetch), with an upstream remote that has no grant (see "Source trust") or diverged (after `git fetch`, `git rev-list --count @{u}..HEAD` is not 0) is `blocked` with a note, and nothing is pulled. The updater never merges, resets or clones. Then `scripts/install-agent-registry.sh <copy>` runs from the bound checkout. A missing script is `blocked` before any git command. A changed revision is `updated`; the same revision, and the working copy, is `current`. A managed copy that the bound checkout declares as a checkout of the same repository needs no grant (see "Source trust").
- **checkouts** (DFM-25 C01) fast-forwards each `git-checkout/v1` checkout that the profile declares (docs/packages.md, "Git checkouts"). It runs the same git commands as the `agents` managed copy. A checkout follows the branch its clone tracks. The updater never pins a revision, merges, resets, rebases or force-updates. A checkout that the bound checkout declares needs no grant (owner decision of 2026-11-12). A checkout that a nested source of the lock declares needs a grant for its url: without one it is blocked before the fetch with the `E_SOURCE_UNTRUSTED` note, and the other checkouts still run (docs/sync.md, "Source identities"). The upstream remote url must have the source identity of the declared `url`. Both go through the owner's `url.*.insteadOf` rewrites: `git remote get-url` gives the upstream, and `git ls-remote --get-url <url>` in the copy gives the declared url, so a global rewrite (for example `https://github.com/` to `git@github.com:`) applies to both and does not block the checkout. Otherwise the checkout is blocked before the fetch, with the note `<id>: <path> fetches <url>, not the declared <url>; not pulled`, and no grant can allow it. A declaration that is not valid is a note `<id>: <reason>` and makes the row `blocked`; the other checkouts and updaters still run. Each checkout has one note: `<id> <before> -> <after>`, `<id> current at <rev>`, or the blocked note, which names the path. A dirty, diverged or upstream-less checkout is left as it is, and the other checkouts still run. A checkout without `.git` has the note `<path> is not cloned yet; the packages scope clones it` and runs no command. The packages scope clones a missing checkout and never pulls. When the profile also declares `agents`, a checkout at the `agents` managed copy is left to that updater, which pulls it before its install; otherwise `checkouts` pulls it. A declared checkout at or inside the bound checkout or a nested source checkout of the lock is the note `<id>: <path> is a dotfiles source checkout; sync updates it`. Git runs with `GIT_CEILING_DIRECTORIES` set to the copy's parent, for `checkouts` and `agents`. The fetch and the pull also get `SSH_AUTH_SOCK` when the manager's own environment has it; no other git call does. Before any other git command, the copy's own configuration (`git config --list --local`) must pass the allowlist of docs/sync.md, "Checkout configuration". A key outside it (`core.sshCommand`, `core.fsmonitor`, `include.path`) blocks that copy before the fetch, with the note `<noun> <path> configures <key>, ...; not pulled`, and the other checkouts still run. The preview counts invalid declarations: `would fast-forward 1 checkout (<path>); 1 declaration invalid`. The row is `failed` when a checkout failed, else `blocked` when one is blocked, else `updated` when one moved, else `current`. A missing `git` is `blocked` before any command.
- **brew** upgrades every outdated formula and cask, not only declared ones. A name that `brew outdated --json=v2` marks `"pinned": true` (`brew pin`) is left out of the upgrade and its check, with the note `formula node held (brew pin)`. Version-sensitive tools are pinned with mise, per project or globally. `brew upgrade` gets the outdated names, one call per kind, so each formula and each cask is accounted for as itself, also when a formula and a cask share a name. Notes read `formula uv 0.13.5 -> 0.13.6 upgraded` or `cask codex 0.164.0 still outdated (0.165.0)`. An empty list is `current` and runs no upgrade. Homebrew runs with its defaults (the dependents check and cleanup stay on). The manager sets `HOMEBREW_NO_ANALYTICS=1` and `HOMEBREW_NO_ENV_HINTS=1`, and `HOMEBREW_NO_AUTO_UPDATE=1` for every command after `brew update`.
- **A native tool** (`claude`, `codex`, `opencode`) must exist at its owner path. If it does not, it is `blocked` with that path, and no other copy (for example the Homebrew cask) is used. The runner's executable checks apply: a link that leaves the owner's prefix is `blocked`.
- **A second copy.** For each native tool, `brew list --versions` and `brew list --cask --versions` look for a Homebrew copy under Homebrew's name for it: the cask `claude-code` (the `claude` cask is the desktop app), the formula and cask `codex`, the formula `opencode`. The check runs after every updater ran, so the version is the one `brew` left, and each copy found is a line after the rows (`  note: codex second copy: Homebrew cask codex 0.165.0`). It is never removed or chosen.
- **skills** reports no version. Exit 0 is `current` with the note `skills update ran; it reports no version`.
- **side-channels** runs the bound checkout's `sync-side-channels` recipe. The recipe name is fixed in the manager; the checkout is the one sync fast-forwarded from a granted origin, as for the `agents` install script, so it needs no grant of its own. A missing `Justfile` or `just` is `blocked` before any command. It reports no version: exit 0 is `current` with the note `sync-side-channels ran; it reports no version`; another exit is `failed`. The 30-minute timeout applies. It runs detached like every updater, so a step in the recipe that needs a terminal (an `op signin` prompt) does not get one. Declare it last to run it after the other updaters.
- **mise** (DFM-85) first installs the configured tools that are missing (`mise install`), then upgrades every tool the configuration requests: the global files and any file mise reads from the runner directory under HOME and its parents, such as `~/.tool-versions`. The mise configuration is the owner's own file, so the updater runs without a grant (owner decision of 2026-11-12). `mise upgrade` runs without `--bump`, so each tool moves to the newest version inside its configured range (`go = "1.27"` stays on 1.27.x) and no configuration file is written. mise removes the replaced version after its own grace period (the `upgrade.prune_after` setting, 24 h by default) unless a configuration mise has seen still requests it; the "no version is removed" rule of docs/toolchains.md is `packages --update`'s, not this updater's. A declared `mise/v1` package or a mise trial is installed with `mise install <tool>@<selector>` and is not in the configuration, so the mise updater does not touch it: `packages --update` rolls it. `mise ls --installed --json`, which reads the install directory and fetches nothing, runs before and after `mise install`. Each tool version the install adds is a note (`node 22.1.0 installed`) and makes the row `updated`, also when nothing is outdated. A listing that fails makes the row `failed`. Statuses otherwise follow brew: `mise outdated --json` before and after, `updated` when every outdated name left the list, `failed` when one stays (`go 1.27.3 still outdated (1.27.4)`), `current` on an empty list without an upgrade and without a new install.
- **rustup** (DFM-85) must exist at `~/.cargo/bin/rustup`, the path rustup.rs installs to (the mise shim is not used). `rustup check` lists every installed toolchain and rustup itself; it exits 100 when an update is available and 0 when none is, and both are read as the list. `rustup update` updates every installed toolchain and rustup itself. No toolchain is removed. Statuses follow brew, by toolchain name.
- **uv** (DFM-85) upgrades each tool under `~/.local/share/uv/tools`, one `uv tool upgrade <name>` each, so one failed tool leaves the others their upgrade; the row is then `failed` with that tool's exit code. A tool from a git source needs a grant (see "Source trust"). `uv` runs with `UV_PYTHON_DOWNLOADS=never`, as under `packages --update`. `uv tool list` before and after decides the status: a changed version is `updated` (`b 2.0 -> 3.0 upgraded`), the same listing is `current`. A tool pinned to a revision (`?rev=`) stays there and is `current`. No tool is `current` with the note `no uv tool is installed`.
- **npm** (DFM-85) upgrades the global packages. Each package needs an `npm:<name>` grant (see "Source trust"). `npm` itself is held, because Homebrew's node formula owns `/opt/homebrew/lib/node_modules/npm` (`npm 11.20.0 held (Homebrew's node formula owns it; latest 12.2.2)`); a package already at its `wanted` version is held there (`<name> <v> held at wanted (latest <l>)`), because `npm update` reaches no further. `npm outdated -g --json` exits 1 when a package is outdated, and that exit is read as the list; an error document (`{"error": ...}`, a failed registry request) or an entry without `current` or `wanted` fails the row instead, before or after the upgrade. Every npm command runs with `npm_config_registry`, and `npm_config_@<scope>:registry` for each scope among the global packages, set to the default registry, as `skills` does for the registry, so neither a registry nor a scoped registry an npmrc names can serve a package the grant covers. Statuses follow brew: `updated` when every outdated package left the list, `failed` when one stays.

## Source trust

`skills` and `agents` fetch extension sources and run what they fetch, a global npm package runs its install scripts, and a uv tool from a git source is built from what it fetches. Each such source needs a grant in `state/grants.json` before the updater runs (DFM-25, C04; the identities are in docs/sync.md, "Source identities"). `claude`, `codex`, `opencode`, `brew`, `mise` and `rustup` update a binary or the packages from their owner and are not gated; so is a uv tool from a local directory or an index name.

| Updater | Sources, read without running a command |
| --- | --- |
| `skills` | `npm:skills`, the installer that `npx` runs, and the `source` and `sourceUrl` of every entry of the `skills` CLI's source record |
| `agents` | the managed copy's upstream remote: the remote that `branch.<branch>.remote` names, resolved with `git remote get-url <remote>`, so `url.*.insteadOf` rewrites apply. The working copy is never fetched and is not checked: it is the owner's own checkout. A managed copy that a `git-checkout/v1` resource of the bound checkout declares, with a `url` of the same source identity as the upstream url, is not checked either. One that a nested source declares is checked |
| `npm` | `npm:<name>` for each global package that `npm ls -g --depth=0 --json` lists (a local command, no network, run with `npm_config_link=false` so an npmrc `link=true` cannot narrow it), except `npm` itself, which is held. An outdated package the listing did not hold is not updated: the row is `blocked` and names it |
| `uv` | the `git` entries of every source list under `[tool]` in each tool's `~/.local/share/uv/tools/<name>/uv-receipt.toml` (`requirements`, `constraints`, `overrides`, and any list a newer uv records; an upgrade resolves each again), the `?rev=` query removed, mapped as it is and then as git fetches it (`git ls-remote --get-url`, so `url.*.insteadOf` rewrites apply, as for `skills`). A `directory`, `editable` or index requirement needs none. A `url` archive maps to no identity, and so does a legacy receipt whose entry is one PEP 508 string (reinstall the tool to get a table receipt) or a receipt that cannot be read: the row is `blocked` with the tool's name |

- **The `skills` source record** is `~/.agents/.skill-lock.json`, as `skills` 1.7 writes it: `{"version": 3, "skills": {"<name>": {"source": "o/r", "sourceType": "github", "sourceUrl": "https://github.com/o/r.git", ...}}}`. `skills update` reads it for the global skills. The updater's environment is cleared, so `XDG_STATE_HOME`, which would move the record, is not set. The updater runs in the manager's cache directory, which holds no `skills-lock.json` or `.agents/skills`, so `skills update` takes the global scope and not a project's. A missing or unreadable file, invalid JSON, a `version` other than 3, an entry without a text `source`, or a `sourceUrl` that is not text is a record this manager cannot read.
- **The `agents` upstream** is read with local git commands only (`rev-parse`, `config`, `remote get-url`), before any fetch. A remote whose url git cannot give is `blocked` with the cause. The fetch and the pull name the checked remote and branch (`git fetch <remote>`, `git pull --ff-only <remote> <merge>`), so git cannot choose another remote between the check and the fetch. The upstream's grant covers the pull and the registry's own install code.
- Each source without a grant, and each source that maps to no identity (a local path, a well-known skill domain), makes the row `blocked`, and the updater runs no command. One note per source: `E_SOURCE_UNTRUSTED: no grant for npm:skills; review it, then run dfm sync --trust-origin 'npm:skills'`.
- A source record that cannot be read makes the row `blocked` with the cause, for example `cannot read ~/.agents/.skill-lock.json: entity not found; nothing ran`. It is never `current`, and the updater never runs without the check.
- The check runs in the listing before publication and again under the writer lock just before the updater runs, with the grants read under the lock, because the record or the grants can change between them.
- **A git source maps only to a git origin.** The `agents` upstream url and each skill source must map to an `https`, `ssh` (or test `file`) origin. Git reads `npm:skills` as the SCP form (host `npm`), so a git url that maps to an `npm:` identity is `E_SOURCE_UNTRUSTED`: an npm grant never covers a git fetch.
- **A skill source is checked as git clones it.** Each `source` and `sourceUrl` is first mapped as it is, so a value that maps to no git origin never reaches git. Then `git ls-remote --get-url <url>` (local, no network call) gives the url git fetches from after the user's `url.*.insteadOf` rewrites, and that url's identity needs the grant. A GitHub shorthand `o/r` is resolved as `https://github.com/o/r.git`, the url the `skills` CLI clones. A missing `git`, or a call that fails or prints no url, makes the row `blocked` with the cause. The listing resolves the same way.
- One updater fetches all of its sources, so one ungranted source blocks the whole row.
- `skills update` runs with `npm_config_registry=https://registry.npmjs.org/`, which overrides every npmrc, so `npx` fetches `skills` from the default registry that an `npm:` grant names.

## Tracked files

An updater must not leave a tracked file changed in a source checkout without the owner knowing (DFM-25, C05).

- Before the first updater, sync records a snapshot of the bound checkout and each nested source checkout that the published lock declares: `git status --porcelain=v1 -z --untracked-files=no` (with `--no-optional-locks`, through the scrubbed git of docs/sync.md), plus the type and content of each path it lists: `git hash-object --no-filters` for a file, the target for a symlink. Status alone is not enough, because an updater that rewrites a file that is already modified leaves its status line as it was. After each updater that ran, sync records the snapshot again and compares.
- A tracked file that the updater changed (a new or changed status line, new content or a new type, or a change back to the committed form, shown as `restored`) makes that row `failed` with one note per file: `E_CONFLICT: claude changed the tracked file <checkout>/<path> (M); it is left in place, not reverted, staged or committed`. A file that resolves through a dfm link into a checkout shows as the file in the checkout.
- The change stays for the owner. Sync does not revert, stage, commit or push it. The next `dfm sync` refuses an update that would overwrite it (docs/sync.md, step 2).
- The other updaters still run. A `blocked` updater ran no command and is not compared. A status that cannot be read after an updater fails that row with the cause; one that cannot be read before the first updater is an error of the step (`upgrade: failed (<code>)`).

## Statuses

| Status | When |
| --- | --- |
| `updated` | the version changed (brew: every upgraded name left the outdated list) |
| `current` | exit 0 and the same version (brew: nothing outdated) |
| `pending` | a stop request (SIGINT, SIGTERM) ended or prevented it, or the update ran and the new version could not be read |
| `failed` | a command exited nonzero (checkouts: for one checkout), timed out or was ended by a signal; the updater changed a tracked file in a source checkout (`E_CONFLICT`, see "Tracked files"); brew: a name stayed outdated or the list was not valid JSON |
| `blocked` | skills, agents, npm, uv: a source has no grant or maps to no identity, or the source record cannot be read (see "Source trust"); agents: the install script or `git` is missing, or the managed copy is missing, dirty, without an upstream or diverged (local commits); checkouts: `git` is missing, a declaration is not valid, or a checkout is dirty, without an upstream, diverged or tracks a url other than the declared one, or a nested source declared it and its url has no grant; the tool, or `mise` for skills, is missing from its owner path, fails the executable checks, or its version cannot be read (or is empty) before the update; brew, mise, uv, npm: the program cannot be resolved on the provider path; rustup: `~/.cargo/bin/rustup` is missing |

A failure note gives the command, its exit code and the size of its standard error. The text is withheld (docs/secrets.md); run the command by hand to see it. A partial `brew upgrade` is `failed`, and the notes list each name as upgraded or still outdated.

## Trials

A trial does not hold `brew`. The owner's decision of 2026-10-31 replaces DFM-31.C09: a tool is trialed without an effect on any other update, and it is updated with the other packages as if it were already adopted. `brew` runs as if no trial existed and upgrades a trial's formula or cask with every other outdated package. No updater reads the trial records, so an unreadable record or an interrupted trial write does not change the run. A missing trials directory still refuses the whole run before any scope, as state loss (`E_STORAGE_INVALID`): the store refuses every writer on a missing state directory (docs/state.md). A `mise/v1` trial is rolled by `dfm packages --update`, not by `sync` (docs/toolchains.md, "Trials").

## In sync

1. After the plan, before publication and the scopes, each updater is listed with what it would run and its resolved path, or `blocked: <why>` (DFM-31.C02), the source check included. Every declared updater is listed, a blocked one too (DFM-25, G6). Nothing runs yet.
2. The four scopes run as docs/sync.md describes.
3. A refused run (an error exit) runs no updater. A skipped or blocked scope does not stop them.
4. `--no-upgrade` prints `upgrade: skipped (--no-upgrade)` and runs none.
5. The step also runs after "nothing to change".
6. Under the writer lock, the profile is resolved again from `--root`, because another sync may have changed it since the review. An updater runs only when the review listed it and the profile still declares it; one added meanwhile runs in the next sync, after its review. A profile that declared none in the review takes no lock. Each updater that runs prints one row: `  <status> <name> <before> -> <after>`, then its notes. A blocked updater prints its row too and counts in the summary. After the last row, the second copies of the native tools are read (see "The fixed set").
7. One receipt is written (`command = "upgrade"`, no plan digest, no approval), with one operation per updater (`resource = "updater:<name>"`, `adapter = "updater/v1"`). An updater that is not `updated` or `current` makes the receipt `failed`, exit 1, while sync itself exits 0.
8. The `scopes:` block ends with `  upgrade: <status>=<count>...`, and each `failed`, `blocked` or `pending` updater adds a `warning:` line at the end of standard output.
9. A stop request during the step ends that updater, reports the rest `pending`, writes the receipt and ends the run with the stop's exit code (130 or 143). The warnings still print. No journal entry is written, so the next sync runs every updater again.
10. An error of the step itself (the writer lock is held by another command, the state cannot be read, the receipt cannot be written) keeps the scope summary, reports `upgrade: failed (<code>)` and exits with that error.

`--preview` lists each updater with what it would run and its resolved path, and runs nothing.

Updaters run detached: each starts in a new session (`setsid`, `Runner::detach`), with no controlling terminal and standard input closed. A step that needs a password or a prompt, such as a cask whose installer runs `sudo`, fails at once instead of waiting at the terminal. The `brew` row names the package that stayed outdated. Upgrade it by hand.

Timeouts: 30 minutes for each upgrade command (`brew upgrade`, `mise upgrade`, `rustup update`, each `uv tool upgrade`, `npm update -g`), 10 minutes for every other command (the listings, `brew update`, the native tools).

## Known limits

- **No candidate version in the preview.** The newest version is what each provider resolves at run time.
- **`sudo` casks fail** under the detached run.
- **skills reports no version**, so it is never `updated`.
- **The guard sees changes, not their author.** A change that another process makes to a tracked file while an updater runs is counted against that updater.
- **The `skills` record** is read in version 3 only.
- **agents** does not clone a missing managed copy. Clone it by hand. A working copy is installed with its uncommitted changes.
- **Second copies** are looked for in Homebrew only, not in npm or mise, and only for the native tools.
- **mise prunes.** The version `mise upgrade` replaced is removed after mise's grace period (`upgrade.prune_after`). A project configuration mise has not seen yet (not trusted) does not protect its pinned version.
- **rustup self-updates.** `rustup update` replaces `~/.cargo/bin/rustup` when rustup itself has an update. A rustup installed by Homebrew is not used; its row is `blocked`.
- **npm is held**, so the global `npm` is upgraded only by `brew upgrade` of the node formula. A global package whose range stops below `latest` is held at `wanted`.
- **A uv tool from a `url` archive** is `blocked`; upgrade it by hand. The `uv` row names the tool.
- **Evidence scope.** Tests use look-alike updaters. No test runs a real updater. The `agents` sync test uses real git against a local registry remote and a look-alike install script.
