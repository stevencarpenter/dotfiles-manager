# Adopt (DFM-33) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `dfm adopt <trial-id> --module <m>` promotes a trial's configuration files into the dotfiles repo as `fs-link/v1` resources, appends the Brewfile line, replaces the live files with dfm links, and ends the trial.

**Architecture:** A new CLI command `adopt_cmd.rs` follows the shape of `trial_cmd.rs`: decide, preview with a digest, then decide again under the writer lock and write. The repo edits are append-only text operations in a new pure model module. The live-file takeover is a new plan action, `AdoptFile`, that only adopt asks the planner for. The engine's existing `apply` executes it, so there is no second publisher.

**Tech Stack:** Rust workspace (crates `model`, `engine`, `cli`), `rustix` `*at` calls, the existing `Runner` for `git` and `gitleaks`, integration tests through the isolated `dfm` binary.

**Spec:** `docs/superpowers/specs/2026-10-28-adopt-design.md`

## Global Constraints

- Command line: `dfm adopt <trial-id> --module <module> [--root <dir>] [--preview] [-y|--yes-plan <digest>]`. `--module` is required.
- Exits: 0 done, 1 failure after the first write, 2 usage, 3 blocked before any write, 130 and 143 stop.
- Adopt never commits, pushes, edits the profile, creates a module, or merges modules.
- Repo edits are appends only. Existing manifest and Brewfile bytes stay byte-for-byte unchanged, and the file must parse again after the append.
- Candidates are regular files only. Adopt never declares `directory = true`.
- The secret scan is `gitleaks dir`. A finding, a missing `gitleaks`, or a failed scan blocks adopt (`E_PROBE_FAILED` for missing or failed). The message names the path, never the value.
- `apply` and `sync` keep refusing a regular file at a link target. Their behavior and docs do not change (docs/planner.md rule 5, docs/apply.md).
- Brewfile choice: `<root>/Brewfile.<module>` when that file exists, else `<root>/Brewfile`.
- The module manifest must be inside the `--root` git tree.
- Gate: `scripts/check_all.sh` on the branch head only. Conventional Commits, explicit paths, no attribution lines.

## Review Focus

1. **A `.gitleaks.toml` or `.gitleaksignore` inside the candidate directory.** `gitleaks dir` reads config from the target path, so a planted file could disable the rules. Adopt must scan a manager-owned copy (Task 5 test `a_gitleaks_config_in_the_candidate_directory_is_not_used`).
2. **Re-running adopt after an interruption.** The owner will run the same command again. It must complete, not refuse its own partial work as "uncommitted" or "repo file exists" (Task 6 test `a_second_run_completes_after_a_stop_at_each_boundary`).
3. **A manifest without a trailing newline.** The appended block must start on its own line, and the earlier bytes must not change (Task 3 test `append_adds_a_newline_only_when_the_file_lacks_one`).
4. **A live file edited between preview and approval.** `E_PLAN_STALE`, zero writes (Task 5 test `a_live_file_changed_after_the_preview_is_stale`).
5. **Running `dfm apply` or `dfm sync` after adopt, before the commit.** The link must be current, not a removal or a conflict (Task 5 test `apply_after_adopt_plans_the_links_as_current`).

**Interfaces:**

- Produces: `pub struct Args { trial: String, module: String, root: Option<PathBuf>, preview: bool, yes_plan: Option<String> }`, `pub fn parse_args(&[String]) -> Result<Args, Refusal>`, `pub fn run(ctx: &Ctx, args: &Args, out: &mut dyn Write) -> Result<(), Refusal>`.

**Decision (what the digest covers):** trial id, module, manifest path and its sha256, Brewfile path and its sha256 (or absent), each candidate (HOME path, size, sha256, repo path, resource id), the Brewfile line or "none", the binary identity and the binding stamp. Canonical JSON, SHA-256, as `trial_cmd::Decision::digest`.

**Order of one run:**
1. Bound machine; load the trial record; refuse missing, unreadable, or not active.
2. Resolve the profile (`load_resolved`); refuse a module not in `resolved.modules` with the profile path and `modules = [...]` in the message; refuse a module `module_manifest` does not find.
3. Refuse a manifest outside the `--root` git tree.
4. Candidates from `baseline.paths` (spec, "Candidates"); refuse links, special files, unreadable files, files over 16 MiB; refuse none found (`E_CONFLICT`, "nothing to adopt").
5. Refuse a target that any resolved resource or any active trial's `owned_outputs` claims; refuse a resource id already in the composition; refuse an existing repo source path; refuse a dirty manifest or Brewfile.
6. Scan with `gitleaks`.
6a. Brewfile line: only when `package.adapter` is `homebrew/v1`. `BrewKind::Cask` when `package::probe` reports the recorded package as a cask, else `Formula`. The name is `package::leaf` of the recorded name. A missing `<root>/Brewfile` (and no `Brewfile.<module>`) is `E_CONFLICT` naming the expected path. A `mise/v1` trial gets no line and the preview says so.
7. Build the edited manifest in memory, resolve the composition against it with the new files, and refuse a resolve error.
8. Print the preview (candidates, repo paths, resource ids, Brewfile line, `unknown:` tokens from the record, `plan digest:`). `--preview` stops; no `--yes-plan` stops with `E_APPROVAL_REQUIRED`.
9. Take the writer lock, decide again, compare digests (`E_PLAN_STALE`).
10. Journal intent (`op = "adopt"`, recovery lists the repo paths and the manifest and Brewfile pre-hashes), then write: repo files (exclusive create, live mode), manifest append, Brewfile append, then `apply` of a configuration plan built with `adopt_files` = the candidates, scoped to the new resource ids, with `allow_adopt` = its `AdoptFile` ids. Then `mark_trial_adopted`, journal done, receipt (`command = "adopt"`), the changed repo paths, `result:`.
11. Failpoints between each write: `adopt-after-copy`, `adopt-after-manifest`, `adopt-after-brewfile`, `adopt-after-link`.

### Task 6: Interruption and concurrency

**Files:**
- Modify: `crates/cli/src/adopt_cmd.rs`
- Modify: `crates/cli/tests/adopt.rs`

**Interfaces:**
- Consumes: the journal intent of Task 5 with `recovery` holding the pre-adopt manifest and Brewfile sha256.

**Recovery rule:** when the journal holds an `adopt` intent for this trial with no `done` or `failed` entry, a new run accepts, as its own partial work: a repo source whose bytes equal the live file (or, after the takeover, the file the link points to); a manifest whose bytes equal the recorded pre-hash content plus exactly the planned blocks; a Brewfile likewise; a live path that already is the planned link. Anything else is `E_CONFLICT` naming the path. Nothing is deleted, and nothing is written twice.

- [ ] **Step 1: Write failing tests**
  - `a_second_run_completes_after_a_stop_at_each_boundary`: for each failpoint in Task 5 step 11, run adopt with `DFM_FAILPOINTS=<name>`, see exit 1 or 3, then run the preview and the approval again and see the same end state as `adopts_the_tuicr_shape`. No path is removed in any run.
  - `two_adopts_at_once_one_waits_or_is_locked`: start one adopt held at a failpoint pause (as `crates/cli/tests/state.rs` does for concurrency) and run a second: `E_LOCKED`, zero writes from the second.
  - `a_foreign_edit_during_recovery_is_a_conflict`: after `adopt-after-manifest`, edit the manifest by hand; the next run refuses and names the manifest.
