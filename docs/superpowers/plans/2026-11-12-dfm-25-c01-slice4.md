# DFM-25 C01 slice 4: manage the package managers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `dfm sync` rolls each package manager and everything it installed to the newest version, with no per-package grant, pin or adapter: `skills`, `npm` and `uv` lose their per-package grant gates; `skills` runs `skills@latest`; new `go` and `cargo` updaters roll every installed binary; `codex` also upgrades its plugin marketplaces.

**Architecture:** Changes stay in the fixed updater set (`crates/cli/src/adapters/updater.rs`, `crates/model/src/updater.rs`). Two new updaters follow the existing list-then-upgrade pattern (`roll`, `uv`). The per-package trust arms leave `trust_notes`; grants stay for the dotfiles checkout's origins and for sources that a nested source declares (`owner_declared`, PR #102).

**Tech Stack:** Rust (`dfm-model`, `dfm-cli`), shell look-alikes in the updater tests.

**Spec:** `docs/superpowers/specs/2026-11-11-dfm-25-c01-side-channels-design.md`, superseded for slice 4 by the owner decisions of 2026-11-12: user experience first; manage the package manager, not the package (no per-tool adapter, pin or accommodation, especially per `*-axi` tool); drop the per-package grants of `npm`, `uv` and `skills`. Task 1 records this in the spec, replaces the spec's `skill-source/v1` and `codex-plugin/v1` parts, and records the owner's deferral of fantasy-sports (slice 3) to summer 2027.

## Global Constraints

- No per-package adapter, pin, grant or special case. An updater acts on everything its package manager lists.
- A document cannot add a command (G4). New commands: `npx skills@latest update`; `go version -m <bin>`; `go install <module>@latest`; `cargo install --list`; `cargo install <crate>` (and `--git <url>` for a git install); `codex plugin marketplace upgrade`.
- Grants stay only for the dotfiles checkout's origins (sync step 1) and for sources a nested source declares (PR #102). The existing npm registry forcing stays (the owner dropped only the three grant gates).
- One package that fails its upgrade fails the row with its note; the others still upgrade.
- Commit messages: Conventional Commits ending in "(DFM-25 C01)", no attribution. Gate the head only. Docs: short sentences, no em or en dash.

## Review Focus

1. A go binary built from a local directory or with `(devel)` as its version has no module to fetch: it is held with a note, never reinstalled from elsewhere. (Task 2, `go_holds_a_binary_without_a_module_version`.)
2. A cargo crate installed from a git repository or a local path is reinstalled from the same source kind, or held with a note; never replaced by a crates.io crate of the same name. (Task 3, `cargo_keeps_a_git_or_path_crate_on_its_source`.)
3. An empty `~/go/bin` or no cargo installs is `current` with a note, not `failed`. (Tasks 2 and 3.)
4. A missing `go`, `cargo` or `codex` is `blocked` before any command, as for the other updaters. (Tasks 2 to 4.)
5. With the grant gates gone, `npm`, `uv` and `skills` with an empty `state/grants.json` run and report as before. (Task 1, `npm_uv_and_skills_run_without_grants`.)

### Task 2: the `go` updater

**Files:** `crates/model/src/updater.rs` (`Updater::Go`, name `go`), name lists in `resolve/docs.rs` and `cli/src/lib.rs`, `crates/cli/src/adapters/updater.rs` (`go`, preview, `owner_dir`/`second_copies` arms), `docs/upgrade.md`, `README.md`.

**Interfaces:** `fn go(d: Draft, env: &Env) -> Row`. `go` is a mise shim on the M5, and mise sets `GOBIN` to the versioned Go install directory (`~/.local/share/mise/installs/go/<version>/bin`), which a Go patch upgrade replaces. So every go command runs as `mise exec -- go ...` with `GOBIN=<HOME>/go/bin` set by dfm, and the binaries listed and reinstalled are those in `~/go/bin`. A missing `mise` is `blocked`.

- [ ] **Step 1: Failing tests** with a `go` look-alike whose `version -m <bin>` prints `path`, `mod <module> <version>` lines from a fixture and whose `install <path>@latest` updates that fixture:
  - `go_reinstalls_each_binary_at_latest`: two binaries; calls `go install <path>@latest` once per binary, with the `path` line (the package path, for example `github.com/perplexityai/bumblebee/cmd/bumblebee`); notes `<bin> <old> -> <new>`; status `updated`; a binary already at latest is `current`.
  - `go_holds_a_binary_without_a_module_version`: `(devel)` or no `mod` line: held with a note, not installed.
  - `go_with_no_binaries_is_current`.
  - `go_missing_is_blocked`.
  - One failing install fails the row and the others still run.
- [ ] **Step 2: Run** and expect FAIL.
- [ ] **Step 3: Implement.** List the regular files in `~/go/bin`. Run `mise exec -- go version -m <bin>` on each, and skip a file that is not a Go binary. Group the binaries by package path. Run `mise exec -- go install <path>@latest` with `GOBIN=<HOME>/go/bin`. Then run `go version -m` again to read the version after the install. Set no other Go variable.
- [ ] **Step 4: Run**, expect PASS.
- [ ] **Step 5: Docs** (table row, bullet, README list).
- [ ] **Step 6: Commit** `feat(upgrade): roll every go-installed binary to latest (DFM-25 C01)`.
